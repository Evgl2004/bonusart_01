# Дорожная карта автосценариев купонных акций SAGUR

Дата черновика: 2026-05-25.

Документ описывает техническую доработку, которая позволит запускать постоянные купонные акции без ежедневных ручных кампаний и без шума в отчетности.

## 1. Зачем нужен отдельный контур автосценариев

Текущая ручная рассылочная кампания хорошо подходит для пилотов и разовых маркетинговых гипотез. Но постоянные акции вроде "День рождения" или "Заполни дату рождения" не должны требовать ежедневного ручного запуска.

Проблема ежедневных кампаний:

- маркетолог превращается в оператора кнопки;
- отчеты распадаются на много мелких кампаний;
- можно пропустить день;
- сложно смотреть эффективность акции целиком;
- сложно управлять лимитами частоты контакта с гостем.

Цель автосценария: маркетолог один раз утверждает правила, а SAGUR регулярно сам выбирает подходящих гостей, выдает купоны, отправляет сообщения и собирает отчет.

## 2. Что уже есть в системе

Автосценарии не нужно строить с нуля. В SAGUR уже есть фундамент:

| Блок | Статус | Что дает |
|---|---|---|
| `NotificationScenario` | Реализован | Настройки автоматического сценария. |
| `NotificationEvent` | Реализован | Факт срабатывания сценария, дедупликация, planned_send_at. |
| `DispatchTask` | Реализован | Универсальная очередь доставки в Telegram, MAX, VK. |
| `run_notification_scenarios` | Реализован | Плановый запуск зарегистрированных сценариев. |
| `inactive_30d_coupon` | Каркас | Есть точка расширения `coupon_resolver`, но нет реальной выдачи купонов. |
| Купонная кампания SAGUR | Реализована | Назначение купонов, sync-gate, vtelemax ACK, отчеты. |
| `CouponVtelemaxSyncQueue` | Реализована | Очередь событий `assignments` и `status_update` во vtelemax. |
| `sync_coupon_redemptions` | Реализован | Сопоставление OLAP/order_fact с купонными назначениями. |
| `close_coupon_campaigns` | Реализован | Закрытие купонов после окончания окна кампании. |

Главная доработка: связать существующий контур `NotificationScenario` с реальной купонной выдачей и отчетностью по акции.

## 3. Целевая модель

Автосценарий должен быть не ежедневной ручной кампанией, а правилом:

```text
правило отбора гостей
-> проверка лимитов и исключений
-> резервирование купона
-> отправка assignment во vtelemax
-> после ACK постановка сообщения в DispatchTask
-> доставка гостю
-> контроль применения через OLAP
-> закрытие/expired/canceled/used_after_campaign
-> агрегированный отчет
```

Внутри можно использовать существующие технические сущности, но пользовательский отчет должен группироваться по автосценарию, а не только по отдельной технической волне.

## 4. Режимы работы автосценария

| Режим | Что делает система | Для чего нужен |
|---|---|---|
| Только отчет | Считает, кто попал бы в сценарий, но ничего не отправляет. | Проверить объем и качество аудитории. |
| Пилот | Ограниченно выдает купоны и отправляет сообщения, с ручным подтверждением правил/первого запуска. | Безопасно обкатать механику. |
| Автоматически | Сам регулярно выбирает гостей и отправляет сообщения по утвержденным правилам. | Штатная работа доказанной акции. |
| Пауза | Не делает новых выдач, но сохраняет отчеты и может закрывать старые купоны. | Безопасная остановка. |

## 5. Минимальные настройки автосценария

| Настройка | Пример |
|---|---|
| Название | "День рождения" |
| Код | `birthday_coupon` |
| Статус | черновик / пилот / активен / пауза / завершен |
| Режим | только отчет / пилот / автоматически |
| Аудитория | гости с согласием, дата рождения в окне |
| Расписание проверки | каждый день в 10:00 |
| Окно отправки | 09:00-21:00 |
| Лимит за проход | например 200 гостей |
| Лимит частоты | не чаще 1 раза в год для birthday, 1 раза в 30 дней для winback |
| Серия купонов | фиксированная серия или правило выбора серии |
| Область действия | по сети (`global`) или конкретное заведение |
| Срок действия купона | например 14 дней или до конца birthday-окна |
| Текст сообщения | шаблон с переменными |
| Боты | все активные или основной бот |
| Правила исключения | уже есть активный купон, доставка недоступна, недавно получал эту акцию |

## 6. Предлагаемая архитектура

### 6.1. Не плодить новую отправочную очередь

Отправка сообщений должна оставаться через `DispatchTask`. Это уже проверенный контур:

```text
NotificationEvent / MailingGuest
-> DispatchTask
-> dispatch_universal_tasks
-> provider worker
```

### 6.2. Использовать `NotificationScenario` как ядро, но добавить купонную конфигурацию

Варианты:

1. Расширить `NotificationScenario.settings` для купонных сценариев.
2. Добавить отдельную связанную модель `CouponAutomationConfig`.

Рекомендация: для пилота можно начать с явной связанной модели или хорошо валидируемой структуры settings. Если сценариев станет больше, отдельная модель будет удобнее для UI и отчетов.

Нужные поля купонной конфигурации:

- `coupon_series`;
- `venue_code`;
- `venue_name`;
- `coupon_validity_days` или правило `valid_until`;
- `coupon_promo_text_template`;
- `min_order_amount` как справочная настройка для маркетолога;
- `iikocard_action_note` - что настроено в iikoCard;
- `release_policy`;
- `close_policy`;
- `max_active_coupons_per_guest`;
- `cooldown_days`.

### 6.3. Добавить техническую волну без пользовательского шума

Автосценарий может создавать внутренний "run" или "wave":

- дата запуска;
- сколько гостей найдено;
- сколько исключено;
- сколько купонов зарезервировано;
- сколько ACKed во vtelemax;
- сколько сообщений доставлено;
- сколько купонов применено.

Этот run нужен для аудита, но в пользовательском интерфейсе основной отчет должен быть по автосценарию целиком.

## 7. Поток выполнения

### Шаг 1. Отбор кандидатов

Handler сценария находит гостей по правилам:

- согласие на сообщения;
- доступный бот-канал;
- сегмент/условие;
- нет активного купона этой акции;
- не нарушен cooldown;
- есть доступная серия купонов.

### Шаг 2. Резервирование купона

Система выбирает доступный купон из `CouponRegistryEntry` и создает назначение:

- текущий ручной контур использует `CouponCampaignAssignment`;
- для автосценариев нужно решить: использовать эту же модель с nullable campaign или добавить отдельную модель назначения.

Рекомендация для проектирования: не привязывать автосценарии жестко к `Mailing`, иначе мы снова получим шум кампаний. Можно переиспользовать большую часть логики назначения, но источник должен быть "автосценарий".

### Шаг 3. ACK vtelemax до сообщения гостю

Как и в ручных кампаниях:

1. SAGUR ставит `assignments` в `CouponVtelemaxSyncQueue`.
2. Воркер отправляет batch во vtelemax.
3. Только после ACK можно отправлять сообщение гостю.

Это обязательный sync-gate, чтобы сообщение не ушло раньше, чем купон появился в боте.

### Шаг 4. Отправка сообщения

После ACK создается `DispatchTask` с текстом сообщения.

Сообщение должно использовать тот же шаблонизатор, что и ручные рассылки:

- имя гостя;
- код купона;
- название заведения;
- дата действия;
- стандартный текст про меню "Купоны" в профиле.

### Шаг 5. Контроль использования

Существующий контур:

- OLAP control pull;
- OLAP sync worker;
- order_fact;
- `sync_coupon_redemptions`;
- status_update во vtelemax.

Для автосценариев нужно расширить сопоставление так, чтобы отчет агрегировался по сценарию.

### Шаг 6. Закрытие срока действия

После окончания срока действия конкретного купона:

- если купон отправлен и не использован: `expired`;
- если купон был зарезервирован, но сообщение не ушло и сценарий отменен: `canceled` + release только после ACK;
- если факт использования пришел после истечения: `used_after_campaign`.

## 8. Первые автосценарии

### 8.1. Заполни дату рождения

Нужно два связанных действия:

1. Отправить просьбу заполнить дату рождения.
2. После появления даты рождения выдать купон-награду.

Техническая задача:

- определить источник события "дата рождения появилась": vtelemax recipients delta, iiko profile sync или локальное изменение гостя;
- добавить дедупликацию, чтобы не награждать повторно за уже заполненную дату;
- связать факт заполнения и выдачу купона в отчете.

### 8.2. День рождения

Ежедневный сценарий:

- выбрать гостей, у которых день рождения попадает в окно;
- проверить, что в текущем году birthday-купон еще не выдавался;
- выдать купон;
- отправить поздравление;
- закрыть купон после окончания окна.

### 8.3. Остывшие 30-60 дней

Плановый сценарий:

- выбрать гостей с последним визитом 30-60 дней назад;
- исключить тех, кто недавно получал winback;
- выдать купон на подарок при заказе от минимальной суммы;
- измерить возврат и оплаченную сумму.

## 9. Отчетность

Нужен отдельный отчет по автосценарию:

- период;
- найдено кандидатов;
- исключено по причинам;
- выдано купонов;
- ACKed во vtelemax;
- доставлено сообщений;
- применено купонов;
- использовано после срока;
- истекло;
- отменено;
- оплаченная сумма заказов;
- средний оплаченный чек;
- позиции в заказах;
- динамика по дням;
- ошибки доставки;
- недоступные контакты.

Также нужен drill-down:

- конкретный гость;
- конкретный купон;
- конкретный dispatch;
- конкретный OLAP/order_fact.

## 10. Защита от давления на гостя

Обязательные правила:

- не отправлять одну и ту же акцию чаще заданного периода;
- не отправлять несколько купонных автосценариев одному гостю в короткое окно;
- не выдавать новый купон, если у гостя уже есть активный купон этой акции;
- исключать гостей с повторными недоставками;
- учитывать отписки и изменения согласий из vtelemax.

## 11. План доработки

### Этап 0. Зафиксировать бизнес-правила

Результат:

- утверждены первые 3 акции;
- согласованы подарки, сроки, минимальные суммы, серии купонов;
- понятны KPI пилотов.

### Этап 1. Проектирование данных

Результат:

- выбрана модель: расширение `NotificationScenario.settings` или отдельная `CouponAutomationConfig`;
- описаны связи с купонами, событиями, dispatch и отчетом;
- определены статусы автосценария.

### Этап 2. Купонный resolver для сценариев

Результат:

- `inactive_30d_coupon` и новые сценарии умеют получать купон из реального пула;
- создается купонное назначение;
- работает sync-gate vtelemax;
- сообщение не уходит до ACK.

### Этап 3. Режим "только отчет" и пилот

Результат:

- можно посмотреть, сколько гостей попало бы в сценарий;
- можно ограничить первые отправки лимитом;
- можно безопасно включить пилот без ежедневных ручных кампаний.

### Этап 4. Отчет по автосценарию

Результат:

- отчет агрегируется по сценарию, а не по десяткам технических волн;
- есть детализация до гостя/купона/заказа;
- есть отдельный учет недоставок.

### Этап 5. Автоматический режим

Результат:

- сценарий работает по расписанию;
- есть health-check;
- есть предупреждения по очереди, ошибкам vtelemax, нехватке купонов, недоставкам;
- маркетолог управляет правилами и паузой, а не ежедневной кнопкой.

## 12. Что включать не сразу

- автоматическую генерацию новых купонных серий без подтверждения;
- массовую работу с legacy-базой;
- агрессивные скидки на весь заказ;
- автоматический `deleted=1` в iikoCard;
- несколько конкурирующих купонных автосценариев одновременно на одного гостя.

## 13. Практический следующий шаг

1. Согласовать маркетинговый документ по первым акциям.
2. Провести 1-2 ручных пилота через текущие рассылочные кампании.
3. По результатам выбрать первый сценарий для автоматизации.
4. Начать с "Заполни дату рождения" или "Остывшие 30-60 дней", потому что они дадут наиболее понятную проверку данных и отчетности.
