# Проект отслеживаемых ссылок в интерактивных сообщениях

- Дата первоначальной фиксации: 2026-08-24.
- Статус на 2026-08-26: код SAGUR, идемпотентная миграция `0061`, пользовательские формы, отчётность и изолированная производственная инфраструктура реализованы логическими коммитами; локальная регрессия выполняется перед выпуском; серверная и живая платформенная приёмка ещё не завершены.
- Область: новый набор «Оценка + главное меню + ссылка», учёт переходов и защищённый перенаправляющий контур.
- Связанные документы: `MESSAGE_INTERACTION_DECISIONS_2026-08-17.md`, `MESSAGE_INTERACTION_CONTRACT_2026-08-17.md`, `MESSAGE_INTERACTION_WORKLOG_2026-08-18.md`.

## 1. Зачем создан отдельный документ

Действующая первая версия интерактивных сообщений уже принята и работает для наборов «Оценка + главное меню» и «Оценка + купоны». Кнопка внешней ссылки меняет не только клавиатуру, но и способ получения события: браузерный переход не является обратным вызовом кнопки vtelemax.

Поэтому новое расширение нельзя незаметно добавить в действующий контракт. До разработки отдельно фиксируются требования, границы измерения, защита публичной точки, влияние на vtelemax, хранение и отчётность.

Обозначения статусов соответствуют реестру решений:

- **Факт текущей системы** — подтверждено исходным кодом либо действующими платформенными форматами.
- **Согласовано по смыслу** — сформулированная владельцем деловая потребность.
- **Техническая рекомендация** — предпочтительный вариант, ещё не разрешённый к реализации.
- **Открытый вопрос** — требует отдельного решения или проверки.

## 2. Сформулированная потребность

### 2.1. Новый набор

**Утверждено 2026-08-25.** Добавляется третий интерактивный набор:

1. «Нравится».
2. «Не нравится».
3. Кнопка перехода по внешней ссылке, например к бронированию столика.
4. «Меню».

Утверждённая трёхрядная раскладка:

- первый ряд — две кнопки оценки;
- второй ряд — кнопка внешнего перехода;
- третий ряд — «Меню».

Текст ссылочной кнопки выбирается из закрытого предопределённого перечня:

- «Забронировать столик»;
- «Заказать доставку»;
- «Перейти на сайт»;
- «Подробнее».

Все четыре подписи обозначают одно техническое действие внешнего перехода и не создают разные виды событий.

### 2.2. Разные адреса назначения

**Утверждено 2026-08-24.** Адрес назначения не является постоянным свойством набора. Одна рассылка или один сценарий используют один конечный адрес: например, сайт доставки либо страницу бронирования конкретного заведения. Для другого заведения создаётся отдельная рассылка со своим адресом. Маршрутизация разных получателей одной рассылки по разным конечным адресам в первую версию не входит.

Один конечный адрес кампании не означает одну общую отслеживаемую ссылку. Для каждого отправленного сообщения создаётся собственный уникальный служебный адрес, иначе переход нельзя связать с конкретной отправкой. Все такие адреса одной кампании могут вести на один общий конечный ресурс.

Для уже созданной отправки адрес назначения фиксируется неизменяемым снимком. Последующее редактирование кампании не меняет адрес в старом сообщении; штатная замена одного конечного адреса другим для уже отправленной ссылки не предусматривается.

### 2.3. Учёт переходов

**Утверждено 2026-08-24.** Переход по ссылке учитывается аналогично повторяемым навигационным действиям первой версии: каждый допустимый вызов уникального адреса создаёт отдельный технический факт перехода. Запись выполняется перед возвратом перенаправления HTTP 302. Она подтверждает вызов нашей функции перехода, но не доказывает успешную загрузку конечного стороннего сайта.

Требуются как минимум:

- число сообщений, по ссылкам которых был хотя бы один переход;
- число связанных гостей, по ссылкам которых был хотя бы один переход;
- общее число переходов, включая повторные;
- показатели в отчётах соответствующей рассылки или сценария.

### 2.4. Область применения

**Утверждено 2026-08-24.** Новый набор доступен простым рассылкам, купонным кампаниям и автосценариям на современных маршрутах. Для исторических и устаревших маршрутов он запрещён по тем же правилам, что действующие интерактивные наборы.

## 3. Почему существующего обратного вызова недостаточно

**Факт платформ.** Кнопка обратного действия и кнопка-ссылка являются разными типами:

- Telegram: поле `callback_data` создаёт обратный вызов боту, а поле `url` открывает адрес; в одной кнопке выбирается ровно один тип. Официальное описание: <https://core.telegram.org/bots/api#inlinekeyboardbutton>.
- VK: действующие кнопки SAGUR имеют тип `callback`; для открытия адреса используется отдельный тип `open_link`. Точный формат необходимо повторно сверить с актуальной официальной схемой VK перед реализацией.
- MAX: тип `callback` создаёт событие `message_callback`, а тип `link` открывает адрес. Официальное описание: <https://dev.max.ru/docs-api>.

Следствие: при обычной ссылочной кнопке vtelemax не получает тот же обратный вызов, который сейчас формируется для действий оценки, меню и купонов. Прямая ссылка на внешний сайт даст пользователю переход, но SAGUR не получит надёжного события для отчёта.

## 4. Рекомендуемый путь перехода

**Утверждено.** В сообщение помещается не конечный адрес бронирования, а уникальный адрес контролируемого перехода:

```text
https://sagur.24vds.ru/r/v1/<32-символьный-токен>
```

Последовательность:

1. При атомарном создании задачи и интерактивности SAGUR создаёт криптографически случайный токен и неизменяемый снимок подписи и конечного адреса.
2. Мессенджер открывает этот адрес как обычную ссылку.
3. Nginx проверяет версию и форму пути, ограничивает частоту и передаёт запрос отдельной службе переходов.
4. Служба выполняет индексный поиск токена в минимальной таблице ссылок.
5. Для действующей ссылки служба в транзакции сохраняет отдельный факт перехода.
6. Только после успешной записи пользователь получает временное перенаправление HTTP 302 на сохранённый адрес.

Промежуточная видимая страница для обычного сценария не нужна. Она ухудшит путь гостя дополнительным нажатием и не устранит полностью автоматические проверки ссылок.

### 4.1. Точная структура платформенных кнопок

Действующее единое описание `NormalizedInteractionButton` нельзя расширять набором необязательных полей так, чтобы одна кнопка случайно получила одновременно обратное действие и URL. Рекомендуется типизированное объединение двух неизменяемых вариантов:

- обратная кнопка: действие, текст и служебный JSON;
- ссылочная кнопка: текст и уникальный служебный URL.

Ряды нового набора строятся как `callback(l)+callback(d) / link / callback(m)`. Служебный JSON версии 2 создаётся только для `l`, `d`, `m`. Ссылочная кнопка не получает `callback_data`, `payload` действия SAGUR и код `u`.

Платформенные структуры:

```json
{
  "telegram": {"text": "Забронировать столик", "url": "https://<домен>/r/v1/<токен>", "style": "primary"},
  "vk": {"action": {"type": "open_link", "link": "https://<домен>/r/v1/<токен>", "label": "Забронировать столик"}, "color": "primary"},
  "max": {"type": "link", "text": "Забронировать столик", "url": "https://<домен>/r/v1/<токен>"}
}
```

Telegram официально требует выбрать ровно один тип кнопки и поддерживает поле `url`; MAX официально документирует кнопку `type=link` с полями `text` и `url`. Для VK текущая структура `open_link` подтверждается действующими библиотеками и уже используемой схемой клавиатуры, но перед выпуском выполняется изолированная локальная и реальная проверка актуального метода `messages.send`.

## 5. Что доказывает такой переход

Событие доказывает, что уникальный адрес конкретной отправки был запрошен. Оно позволяет связать запрос с исходным сообщением, задачей отправки, рассылкой или сценарием и гостем, которому SAGUR создал ссылку.

Оно не доказывает безусловно, что ссылку нажал именно исходный гость:

- сообщение или ссылка могут быть пересланы;
- клиент мессенджера или защитный сканер может заранее проверить адрес;
- браузер может повторить запрос;
- один человек может открыть ссылку несколько раз.

Поэтому в интерфейсе допустимы формулировки «Переходы по ссылке» и «Сообщения с переходом». Формулировки «Гости точно перешли» и «Прочитали сообщение» недопустимы без дополнительной идентификации.

Утверждён основной способ учёта без дополнительной видимой страницы подтверждения: показываются одновременно уникальный показатель по сообщениям и общее число допустимых запросов. Возможную автоматическую активность следует анализировать отдельно, не скрывая исходные факты переходов из основного хранилища.

## 6. Служебный адрес и защита от подбора

**Утверждено.** Публичный адрес не содержит в открытом виде:

- идентификатор гостя;
- телефон;
- идентификатор интерактивности;
- адрес назначения;
- название заведения или кампании.

Утверждённая техническая форма первой версии:

- версия задаётся отдельной частью пути `/r/v1/`;
- токен формируется из 24 криптографически случайных байтов;
- представление Base64URL без заполнения занимает ровно 32 символа из `A-Z`, `a-z`, `0-9`, `_`, `-`;
- энтропия токена составляет 192 бита;
- токен создаётся один раз и не переиспользуется между сообщениями.

Отдельная HMAC-подпись в первую версию **не включается**. При случайном токене в 192 бита она не усиливает связь с записью базы, но создаёт постоянный секрет, версии ключей и обязанность бессрочно хранить старые ключи ради уже отправленных ссылок. Один ограниченный индексный поиск для правильно оформленного случайного пути является осознанной ценой более простого и долговечного контракта. Поток таких поисков ограничивается Nginx и ресурсами отдельного контейнера.

Токен хранится в строке ссылки в исходной форме, потому что отложенный отправитель должен позднее восстановить полный адрес кнопки. Перенос токена в `DispatchTask.payload`, обратимое шифрование либо вывод токена из последовательного идентификатора создают больше связности и не дают полезной защиты для публичного адреса. Токен не предоставляет доступ к персональным данным: он разрешает только зарегистрировать переход и получить заранее сохранённое перенаправление.

В журналах Nginx и приложения запрещено записывать полный токен, полный путь и конечный адрес. Для сопоставления допускаются внутренний идентификатор ссылки и отдельный идентификатор запроса, сформированный уже после успешного поиска.

## 7. Где размещать службу переходов

### 7.1. Предпочтительная граница

**Утверждено.** Использовать отдельный минимальный контейнер `redirect-bonus`, а не открывать публичный маршрут непосредственно в основном `app-bonus`.

Схема:

```text
Интернет
  → точный путь /r/v1/<токен> на sagur.24vds.ru
  → фильтры и ограничения частоты Nginx
  → контейнер redirect-bonus
  → ограниченная работа с PostgreSQL
  → HTTP 302 на сохранённый адрес
```

Причина выбора:

- любой публичный адрес действительно получает сканирование и случайные запросы;
- Nginx отсекает неверные методы, форму пути, чрезмерную частоту и слишком большие запросы до приложения;
- строгая форма пути отсекает некорректные запросы, а ограничения Nginx сдерживают поток случайных правильно оформленных токенов до единичных индексных поисков;
- отдельный контейнер не позволяет потоку публичных переходов занимать рабочие процессы основного интерфейса SAGUR;
- отказ или перегрузка службы переходов не должны блокировать отчёты, формы и внутренние функции `app-bonus`.

Отдельный контейнер не скрывает публичный маршрут и сам по себе не прекращает сканирование: весь входящий трафик всё равно сначала принимает Nginx. Его назначение — уменьшить поверхность приложения и изолировать ресурсы.

### 7.2. Граница текущих проектов

**Факт структуры проектов.** Корень `webhook_03` содержит производственные конфигурации Docker Compose и Nginx для совместного развёртывания, включая `loyalty_service`; это не основание переносить туда деловую логику.

Рекомендуемое разделение:

- код службы переходов, модели, проверки адресов и отчётные расчёты — в репозитории `loyalty_service`;
- отдельная команда запуска, минимальные настройки Django и отдельная таблица маршрутов — там же;
- описание контейнера, ограничений ресурсов, отдельного имени и маршрута Nginx — в корневых производственных конфигурациях `webhook_03`.

Новый программный каркас и отдельный третий репозиторий для первой версии не требуются.

### 7.3. Минимальная поверхность контейнера

Контейнер должен предоставлять только:

- `GET /r/v1/<токен>` — проверка, запись факта и перенаправление;
- `GET /internal/health` — внутренняя проверка состояния без внешней публикации.

В нём не нужны административный интерфейс, формы, пользовательские сеансы, статические файлы, фоновые работники и остальные маршруты SAGUR. Простое использование того же полного набора настроек и тех же прав базы уменьшит пользу изоляции; для реального ограничения нужен отдельный пользователь PostgreSQL с минимальными правами.

### 7.4. Точная программная граница

В репозитории `loyalty_service` реализованы отдельные модули настроек, маршрутов и WSGI для службы переходов: `loyalty_viewer.settings_redirect`, `loyalty_viewer.redirect_urls` и `loyalty_viewer.redirect_wsgi`. Они переиспользуют модели Django, но имеют отдельный корневой маршрутизатор, сокращённый набор промежуточных обработчиков и отдельные реквизиты PostgreSQL. Контейнер запускает только этот WSGI-модуль и не получает маршруты основного интерфейса.

Пользователю PostgreSQL службы переходов необходимы только:

- `SELECT` для таблицы зафиксированных ссылок;
- `INSERT` для таблицы переходов и право использования её последовательности первичного ключа;
- технический `SELECT 1` для внутренней проверки состояния.

Ему не выдаются права изменения ссылок, чтения гостей, задач, рассылок, шаблонов и событий vtelemax. Миграции выполняются действующим контейнером `migrate-bonus`, а не публичной службой. В производственном Compose отдельная одноразовая служба `provision-tracked-link-db` после миграций идемпотентно создаёт или сужает техническую роль, проверяет отсутствие принадлежащих ей объектов и лишних эффективных прав, после чего разрешает запуск `redirect-bonus`.

### 7.5. Переменные окружения

Основному приложению и отправителям нужны:

- `MESSAGE_TRACKED_LINKS_ENABLED` — разрешение формировать новые ссылки, по умолчанию `False`;
- `MESSAGE_TRACKED_LINK_PUBLIC_BASE_URL` — утверждённый полный префикс `https://sagur.24vds.ru/r/v1/` с завершающей косой чертой;
- `MESSAGE_TRACKED_LINK_ALLOWED_HOSTS` — разделённый запятыми точный перечень допустимых доменов назначения.

Публичному контейнеру отдельно передаются:

- `TRACKED_LINK_SECRET_KEY` — самостоятельный случайный секрет минимального Django-приложения, не используемый как подпись публичной ссылки;
- `TRACKED_LINK_DJANGO_ALLOWED_HOSTS` — точные имена узлов, принимаемые Django;
- `TRACKED_LINK_PG_NAME`, `TRACKED_LINK_PG_USER`, `TRACKED_LINK_PG_PASSWORD`, `TRACKED_LINK_PG_HOST`, `TRACKED_LINK_PG_PORT` — подключение под отдельной минимальной ролью PostgreSQL.

Отключение формирования не ломает уже отправленные ссылки. Публичный контейнер не получает токены Telegram, VK, MAX, секрет vtelemax, реквизиты основной роли PostgreSQL и настройки фоновых очередей. Фиксированные параметры формата токена не выносятся в окружение: их произвольное изменение создало бы несовместимые ссылки.

## 8. Требования к Nginx и HTTP

До приложения должны применяться:

- точный маршрут `/r/v1/<токен>` на действующем домене `sagur.24vds.ru`, направленный только в службу переходов;
- разрешение только `GET`; поведение `HEAD` определяется отдельно и не создаёт событие;
- строгая проверка формы пути и длины токена;
- отдельное ограничение частоты по IP и общий предел потока;
- ограничение числа одновременных соединений;
- короткие тайм-ауты и отсутствие тела запроса;
- отдельный безопасный журнал без полного токена и строки запроса;
- заголовки `Cache-Control: no-store`, `Referrer-Policy: no-referrer` и запрет индексации;
- ограничения процессора, памяти и числа рабочих процессов контейнера.

Начальные эксплуатационные пределы для проверочного развёртывания:

- не более 120 запросов в минуту с одного IP с кратковременным запасом 30 запросов;
- общий предел 200 запросов в секунду с кратковременным запасом 400 запросов;
- не более 10 одновременных соединений с одного IP;
- не более 1 КиБ тела запроса;
- не более 2 секунд на соединение с контейнером и 5 секунд на ответ;
- два рабочих процесса Gunicorn, 256 МиБ памяти, половина ядра процессора и не более 64 процессов контейнера.

Это стартовые защитные значения, а не доказанная производственная ёмкость. До выпуска выполняется нагрузочная проверка: 200 допустимых запросов в секунду в течение пяти минут и кратковременный пик 500 запросов в секунду в течение десяти секунд. Критерии прохождения: отсутствие потерянных принятых переходов и ошибок базы, 95-й процентиль ответа не более 200 мс при штатном профиле, устойчивое ограничение лишнего потока ответом 429 и отсутствие влияния на `app-bonus` и отправителей.

Поведение HTTP фиксируется так:

- допустимый `GET` действующей ссылки — запись перехода и HTTP 302;
- `HEAD` — единый ответ 204 без поиска ссылки и без события;
- остальные методы — 405;
- неверная форма, неизвестный токен или отключённая ссылка — одинаковая минимальная заглушка без раскрытия причины;
- ошибка чтения или записи базы — 503 без перенаправления, потому что молчаливый переход без обещанного учёта нарушил бы назначение функции.

## 9. Безопасность адреса назначения

Служба не принимает конечный адрес из параметра публичного запроса. Она получает его только из заранее созданной записи базы, иначе возникнет открытый перенаправитель, пригодный для фишинга.

При сохранении кампании или сценария адрес должен пройти серверную проверку:

- только абсолютный HTTPS-адрес;
- отсутствие имени пользователя и пароля в адресе;
- допустимый домен из управляемого перечня;
- запрет локальных, служебных и внутренних адресов;
- разумный предел длины.

Перечень разрешённых доменов задаётся отдельной переменной окружения и проверяется по точному нормализованному имени узла. Произвольные шаблоны и автоматическое разрешение всех поддоменов в первой версии не используются. Параметры запроса конечного адреса сохраняются, фрагмент разрешён, поскольку он передаётся только браузеру; имя пользователя, пароль, IP-адрес вместо домена и нестандартный порт отклоняются.

### 9.1. Начальный перечень кандидатов

На 2026-08-26 подготовлен следующий начальный перечень точных доменов назначения без шаблонов поддоменов:

- `rest.market`;
- `susami.rest.market`;
- `uzbechka.rest.market`;
- `gruzinka.rest.market`;
- `china.rest.market`;
- `gruzinka.restoplace.ws`;
- `susami.restoplace.ws`;
- `china.restoplace.ws`;
- `usbechka.restoplace.ws`.

Последнее имя действительно использует форму `usbechka` через `s`: именно такой адрес находится в рабочем исходном коде vtelemax. Подменять его на более ожидаемое написание без фактической проверки запрещено.

Пять адресов `rest.market` предназначены для сайта доставки, четыре адреса `restoplace.ws` — для бронирования столиков. Исходный код vtelemax подтверждает использование восьми адресов заведений. Внешняя проверка 2026-08-26 подтвердила страницы доставки и три страницы Restoplace; проверка `gruzinka.restoplace.ws` завершилась внутренней ошибкой инструмента без диагностического HTTP-ответа, поэтому перед включением требуется отдельный прямой запрос с сервера SAGUR.

Этот перечень является исходным разрешённым набором, а не автоматическим разрешением всех поддоменов `rest.market` или `restoplace.ws`.

Если назначение отсутствует, отключено или признано недопустимым, служба не перенаправляет пользователя на адрес из входного запроса и возвращает безопасную нейтральную ошибку.

## 10. Точная модель хранения

### 10.1. Что переиспользуется

**Утверждено.** Действующая сущность `MessageInteraction` переиспользуется как общий корень интерактивной части конкретного сообщения. Создавать вторую независимую сущность «интерактивное сообщение со ссылкой» не нужно.

Через существующую связь `MessageInteraction → DispatchTask` уже доступны конкретная отправка, гость, рассылка или сценарий и платформа. Дублировать эти ссылки в новых таблицах нельзя.

Горячая таблица `DispatchTask` по-прежнему не расширяется долговременными токенами, адресами и переходами. Решение первой версии уже изолировало взаимодействия от очереди отправки по результатам измерений производственной базы.

### 10.2. Почему нельзя без изменения смысла использовать `MessageInteractionEvent`

Действующая таблица `MessageInteractionEvent` описывает события, поступившие из vtelemax:

- уникальный `event_id` формирует vtelemax;
- `occurred_at` означает время долговечной фиксации обратного вызова во vtelemax;
- действия ограничены `l`, `d`, `c`, `m`;
- результат учитывает правило первой оценки;
- обработка защищена пакетным контрактом и HMAC vtelemax.

Ссылочный переход поступает непосредственно в SAGUR, не имеет события vtelemax и не подчиняется правилу первой оценки. Записывать его в существующую таблицу без добавления источника, изменения времени, ограничений, прав и контракта означало бы смешать два разных происхождения событий.

Особенно важно, что отдельному публичному контейнеру тогда потребовалось бы право добавлять строки в общую таблицу действий `l/d/c/m`. Отдельная таблица переходов позволяет выдать ему только минимальное право записи собственных событий.

### 10.3. Справочник назначений и настройки источника отправки

В закрытый перечень `InteractionButtonSet` добавляется код `rating_menu_link` с пользовательским названием «Оценка + ссылка + главное меню».

**Утверждено 2026-08-26.** Предопределённые назначения хранятся в отдельном управляемом справочнике `MessageInteractionLinkDestination`, а не в программной константе формы и не в свободных полях рассылки.

Минимальные поля справочника:

- `code` — неизменяемый уникальный технический код;
- `name` — понятное пользователю название, например «Сами Сусами — доставка»;
- `label_code` — код одной из четырёх утверждённых подписей;
- `target_url` — конечный HTTPS-адрес длиной не более 2048 символов;
- `is_active` — доступность для новых рассылок и сценариев;
- `created_at`, `updated_at` — служебное время создания и изменения.

В `Mailing` и `NotificationScenario` добавляется одна необязательная внешняя связь `tracked_link_destination` на справочник. Для `rating_menu_link` она обязательна, для остальных наборов должна отсутствовать. Пользователь рассылки выбирает только активную запись из списка и не вводит адрес вручную.

Адрес и код подписи записи нельзя изменять после первого использования. Для нового адреса создаётся новая запись, а прежняя при необходимости выключается для будущего выбора. Это предотвращает незаметную смену назначения у уже настроенной кампании. Человекочитаемое название допускается уточнять без влияния на отправленные ссылки.

При создании конкретной задачи `target_url` и `label_code` дополнительно копируются в неизменяемую `MessageInteractionTrackedLink`. Поэтому уже созданное сообщение не зависит ни от дальнейшего состояния справочника, ни от редактирования кампании.

Начальные записи справочника:

- `delivery_main` — «RestMarket — общая доставка», `delivery`, `https://rest.market/`;
- `delivery_susami` — «Сами Сусами — доставка», `delivery`, `https://susami.rest.market/`;
- `delivery_uzbechka` — «Узбечка — доставка», `delivery`, `https://uzbechka.rest.market/`;
- `delivery_gruzinka` — «Грузинка Нани — доставка», `delivery`, `https://gruzinka.rest.market/`;
- `delivery_china` — «Чина — доставка», `delivery`, `https://china.rest.market/`;
- `booking_gruzinka` — «Грузинка Нани — бронирование», `booking`, `https://gruzinka.restoplace.ws/`;
- `booking_susami` — «Сами Сусами — бронирование», `booking`, `https://susami.restoplace.ws/`;
- `booking_china` — «Чина — бронирование», `booking`, `https://china.restoplace.ws/`;
- `booking_uzbechka` — «Узбечка — бронирование», `booking`, `https://usbechka.restoplace.ws/`.

Начальные строки рекомендуется добавлять идемпотентной миграцией данных. Дальнейшее добавление и выключение выполняется через ограниченную административную панель. Маркетинговый интерфейс получает только выбор активного назначения. Новый адрес на уже разрешённом домене добавляется в справочник; новый домен сначала добавляется в защищённый перечень окружения, а затем в справочник.

Закрытые коды подписей справочника:

- `booking` — «Забронировать столик»;
- `delivery` — «Заказать доставку»;
- `website` — «Перейти на сайт»;
- `details` — «Подробнее».

Справочник не заменяет `MESSAGE_TRACKED_LINK_ALLOWED_HOSTS`. Справочник определяет, что может выбрать пользователь, а настройка окружения остаётся независимой защитной границей от ошибочного или компрометированного административного изменения.

### 10.4. Точные дополнительные сущности

Обоснованы две компактные сущности.

`MessageInteractionTrackedLink` — зафиксированная ссылка конкретного сообщения:

- `interaction_id` — связь один-к-одному с `MessageInteraction` и одновременно первичный ключ строки;
- `public_token` — уникальная строка ровно из 32 разрешённых символов;
- `label_code` — снимок одного из четырёх утверждённых кодов подписи;
- `target_url` — неизменяемый снимок конечного HTTPS-адреса, не более 2048 символов;
- `created_at` — время создания;
- `disabled_at` — необязательное время аварийного вывода ссылки из эксплуатации.

Обычного редактирования `target_url`, `label_code` и `public_token` после создания нет. `disabled_at` не показывается как маркетинговая настройка: это аварийное эксплуатационное действие с отдельным журналированием.

`MessageInteractionLinkTransition` — отдельный допустимый вызов ссылки:

- `id` — внутренний большой автоинкрементный первичный ключ;
- `tracked_link_id` — защищённая внешняя связь с зафиксированной ссылкой;
- `received_at` — серверное время успешной вставки факта в SAGUR.

IP-адрес, пользовательский агент, полный путь, конечный адрес, гость, рассылка и счётчики в строке перехода не дублируются. `received_at` означает время приёма нашей службой, а не доказанное время физического нажатия человеком. Каждый новый допустимый `GET` создаёт новую строку; технической дедупликации переходов нет.

Отдельная сущность ссылки предпочтительнее добавления нескольких необязательных ссылочных столбцов в `MessageInteraction`, потому что:

- строки действующих наборов не получают пустые поля адреса, токена, подписи и отключения;
- публичная служба читает только отдельную минимальную таблицу;
- отдельному пользователю PostgreSQL можно выдать доступ только к таблицам ссылок и переходов;
- широкий адрес назначения и публичный индекс токена изолированы от общего поиска интерактивностей;
- существующий проверенный входящий контур vtelemax не меняет модель своих событий.

Цена решения — одна дополнительная компактная строка только для сообщений нового набора и один индексный переход по связи. До окончательного утверждения эта цена должна быть подтверждена планами PostgreSQL и нагрузочным измерением; формальное наличие двух таблиц само по себе не считается достаточным основанием.

### 10.5. Индексы и планы запросов

В первую миграцию входят только:

- первичный ключ `interaction_id` таблицы ссылок;
- уникальный индекс `public_token` для публичного поиска;
- первичный ключ перехода;
- составной индекс `(tracked_link_id, received_at)` вместо отдельного дублирующего индекса внешнего ключа.

Новые индексы в `DispatchTask`, `Mailing` и `NotificationScenario` не нужны. Отчёт начинает от уже ограниченного набора успешно выполненных задач, проходит по существующей уникальной связи интерактивности и применяет индекс связи переходов. До выпуска на PostgreSQL проверяются планы четырёх запросов: поиск токена, вставка перехода, подсчёт по одной рассылке и подсчёт по сценарию за период. Полные просмотры `DispatchTask` и таблицы переходов для выбранного отчёта недопустимы.

### 10.6. Атомарное создание

Действующее описание `DispatchTaskCreationSpec` расширяется необязательными параметрами зафиксированной ссылки. Для нового набора одна транзакция создаёт задачу, `MessageInteraction` и `MessageInteractionTrackedLink`; ошибка проверки адреса, генерации токена или вставки любой строки откатывает всю конкретную отправку. Молчаливая отправка без обязательной ссылки запрещена.

Пакетный путь сохраняется: задачи, интерактивности и ссылки создаются порциями, а редкий конфликт уникального токена проходит через ограниченную изоляцию конфликта. Работник платформы загружает `message_interaction__tracked_link` вместе с задачей, чтобы не создавать дополнительный запрос на каждое сообщение.

### 10.7. Бессрочная работа и будущее сжатие базы

**Утверждено по принципу 2026-08-24.** Изначально отслеживаемые ссылки работают бессрочно. Для этого компактное соответствие «токен → конечный адрес» сохраняется, пока ссылка должна перенаправлять пользователя.

Если в будущем потребуется сократить объём базы, отдельно рассматриваются:

- архивирование или агрегация старых подробных событий перехода;
- сохранение итоговых счётчиков для отчётности;
- обязательное сохранение компактной строки самой ссылки и её конечного адреса.

Удаление подробной истории не должно автоматически ломать переход. Штатного редактирования или переназначения уже отправленной ссылки нет. Если в будущем ссылка осознанно выводится из эксплуатации либо её соответствие всё же удалено по отдельной политике хранения, служба показывает единую нейтральную заглушку, а не перенаправляет на новый адрес и не раскрывает, существовал ли токен. Рекомендуемый HTTP-статус для осознанно недоступного назначения — 410.

Сторонний ресурс может независимо изменить адрес, вернуть ошибку или прекратить работу. Наша служба подтверждает только перенаправление на сохранённый адрес и не гарантирует доступность внешнего сайта.

Повторять с нуля анализ производственной таблицы задач отправки не требуется. Измерения Р-072 уже обосновали общий корень `MessageInteraction`, отдельное хранение событий и запрет переносить долговременное состояние в `DispatchTask`. Перед окончательным утверждением таблиц остаётся проверить только отличающуюся часть:

- точный минимальный перечень столбцов и ограничений;
- индексный поиск ссылки по публичному токену и планы новых отчётных запросов;
- дополнительный объём повторных запросов, включая возможные обращения браузеров и автоматических сканеров;
- будущую политику архива подробных переходов без удаления рабочего соответствия ссылки адресу;
- минимальные права отдельного пользователя PostgreSQL;
- атомарное пакетное создание задачи, интерактивности и ссылки.

## 11. Влияние на vtelemax

Сама ссылочная кнопка не передаёт событие через vtelemax. Однако vtelemax остаётся участником сценария:

- при нажатии оценки он должен удалить только `l/d`;
- кнопки «Меню» и ссылки должны сохраниться с исходными подписями, рядами и адресом;
- «Меню» должно продолжать работать многократно;
- фактическая клавиатура сообщения остаётся источником визуальной структуры.

**Подтверждено письменным анализом команды vtelemax 2026-08-26:** производственный код Telegram, VK и MAX совместим с клавиатурой `l+d / ссылка / m`. После обработки оценки сохраняются ряды `ссылка / m`. Версия 2 служебного JSON и пакетный контракт vtelemax → SAGUR не меняются; изменение производственного кода vtelemax для согласованного формата не требуется.

Основание из кода vtelemax:

- служебное поле `a` описывает обрабатываемые обратные действия, а ссылочная кнопка не является таким действием;
- для нового набора обрабатываемый состав остаётся `l+d/m`, поэтому используются прежние `ldm`, `dlm`, `mld`;
- общая функция удаления оценок ищет три callback-кнопки одной интерактивности и удаляет только фактические `l/d`;
- Telegram передаёт ей только `callback_data`, VK — полезную нагрузку кнопок типа `callback`, MAX — полезную нагрузку кнопок типа `callback`;
- URL-кнопки возвращают `None` как служебные данные, не попадают в удаляемые позиции и сохраняются исходными объектами вместе с текстом, стилем, рядом и адресом.

Письменный анализ подтвердил следующие платформенные границы:

- Telegram сохраняет исходную URL-кнопку, её подпись, адрес, поддерживаемый стиль и отдельный ряд; текст и вложения сообщения не редактируются;
- VK сохраняет объект `open_link` целиком и поддерживает текстовые сообщения и вложения `photo`, `video`, `audio`, `doc`, `wall`; для иных типов, включая `sticker`, действующий код безопасно прекращает редактирование;
- MAX сохраняет кнопку `link`, текст и прочие вложения обычного текстового сообщения; при непустой разметке текста `markup` действующий код безопасно прекращает редактирование.

Ограничения VK и MAX не требуют изменения текущего согласованного сценария обычных маркетинговых сообщений. Расширение области поддерживаемого содержимого в будущем потребует отдельного анализа vtelemax.

Действующая профильная выборка vtelemax завершилась результатом `144 passed` и подтверждает общий механизм сохранения посторонних кнопок. Она не заменяет автоматические тесты точного набора `rating_menu_link`. На стороне vtelemax до выпуска остаётся добавить проверки обработки `l/d`, кодов версии 2 `ldm/dlm/mld`, преобразования `l+d / ссылка / m` в `ссылка / m`, сохранения ссылки, текста и поддерживаемых вложений, многократной работы `m`, отсутствия события от обычного перехода и безопасных отказов на противоречивых данных.

После реализации SAGUR обязательна живая сквозная проверка одного сообщения в Telegram, VK и MAX. Проверяются трёхрядное отображение, переход по ссылке без callback-события vtelemax, удаление только `l/d`, сохранение ссылки и многократная работа `m`, а также отсутствие ошибок платформенного редактирования.

Полный ответ команды сохранён в `VTELEMAX_TRACKED_LINKS_TECHNICAL_RESPONSE_2026-08-26.md`.

Код действия внешнего перехода в пакет vtelemax → SAGUR не добавляется: факт перехода создаёт служба переходов напрямую.

## 12. Отчётность

Новый блок не смешивается с оценками, открытием меню, открытием купонов или применением купона. Для каждого применимого отчёта нужны:

- сообщения с отслеживаемой ссылкой;
- сообщения с хотя бы одним переходом;
- связанные уникальные гости с хотя бы одним переходом;
- общее число переходов;
- доля сообщений с переходом от числа технически успешных сообщений, содержащих ссылку.

Точный расчёт:

- общий показатель «Сообщений с взаимодействием» является объединением сообщений хотя бы с одним принятым событием vtelemax **или** хотя бы с одним сохранённым ссылочным переходом;
- одно сообщение, у которого есть и оценка, и переход, учитывается в этом показателе один раз;
- знаменатель общей доли остаётся числом технически успешно отправленных сообщений с любым набором кнопок;
- отдельная доля ссылок делит сообщения с переходом только на технически успешно отправленные сообщения набора `rating_menu_link`;
- общее число переходов включает все строки `MessageInteractionLinkTransition` без удаления повторов;
- связанные уникальные гости считаются через существующую цепочку `переход → ссылка → интерактивность → задача → гость`.

Расчёт реализуется запросами `Exists` и агрегатами базы, а не загрузкой множества идентификаторов в память Python. Общий шаблон `message_interaction_metrics.html` расширяется третьим блоком «Переходили по ссылке», поэтому одинаковые определения автоматически применяются к простым рассылкам, купонным кампаниям и автосценариям.

Отчёт обязан пояснять риск автоматических проверок и пересылки адреса. Для бизнес-анализа можно дополнительно показывать первый переход и повторные переходы, но физически удалять повторные факты нельзя только ради более красивого показателя.

## 13. Рассмотренные альтернативы

### Прямая ссылка на бронирование

Подходит только если учёт перехода не нужен. При сформулированном требовании отчётности отклоняется.

### Публичный маршрут в основном `app-bonus`

Технически проще и не требует отдельного контейнера, но валидные публичные запросы будут использовать те же рабочие процессы, что интерфейс и отчёты SAGUR. При текущей закрытой границе основного приложения этот вариант не рекомендуется.

### Отдельный физический сервер

Даёт самостоятельную границу отказа, но увеличивает стоимость эксплуатации, резервирования, мониторинга и доступа к данным. Для первой версии не обоснован до измерения реальной нагрузки. Отдельный контейнер на текущем узле изолирует процессы и ресурсы, но не устраняет общий отказ узла; это ограничение принимается осознанно либо пересматривается после измерений.

### Обработка ссылки как обычного обратного вызова vtelemax

Не является единым переносимым механизмом трёх платформ: ссылочные и обратные кнопки имеют разные типы, а произвольный внешний переход не создаёт согласованное событие `callback`. Отклоняется как основа универсального учёта.

## 14. Состояние реализации и условия выпуска

Техническая схема, состав сущностей, индексы, HTTP-поведение, справочник назначений и исходные ограничения утверждены. Письменный анализ команды vtelemax подтвердил совместимость производственного кода трёх платформ с согласованным форматом.

Владелец проекта 2026-08-26 утвердил реализацию со справочником URL-адресов. Архитектурных вопросов, блокирующих код и идемпотентную миграцию SAGUR, не осталось.

Реализовано:

1. Набор `rating_menu_link`, справочник девяти исходных назначений и неизменяемый снимок ссылки каждой отправки.
2. Атомарное формирование задачи, интерактивности и ссылки; платформенные структуры Telegram, VK и MAX.
3. Минимальная служба `redirect-bonus`, отдельная роль PostgreSQL, точный маршрут Nginx и защитные пределы.
4. Показатели переходов в общем блоке отчётов простых рассылок, купонных кампаний и автосценариев.
5. Выбор активного назначения в формах, защита исторических маршрутов, административная панель, сухой пилот и аудит готовности.
6. Публичный префикс `https://sagur.24vds.ru/r/v1/` и точный начальный перечень девяти разрешённых доменов.

До включения формирования реальных ссылок на рабочем сервере обязательны:

1. Нативная проверка `docker compose config`, применение миграции `0061`, идемпотентный запуск `provision-tracked-link-db` и проверка минимальных прав роли.
2. Проверка `nginx -t`, внутреннего состояния `redirect-bonus`, внешних ответов 410/204/302 и отсутствия токена в журналах.
3. Проверка планов PostgreSQL и числовых пределов фактическим нагрузочным испытанием; это приёмка технических значений, а не новая архитектурная развилка.
4. Автоматические тесты vtelemax точного формата `rating_menu_link`, перечисленные в разделе 11.
5. Положительные, отрицательные и сквозные проверки Telegram, VK и MAX, включая сохранение ссылки после оценки и отсутствие события vtelemax от обычного перехода.

До выполнения этих условий `MESSAGE_TRACKED_LINKS_ENABLED` сохраняется выключенным. Подробная последовательность развёртывания и отката зафиксирована в `MESSAGE_INTERACTION_TRACKED_LINKS_DEPLOYMENT_2026-08-26.md`.
