# Переход SAGUR / Program-Loyal на авторизацию iiko Cloud API версии 2

- Дата анализа: 2026-08-26.
- Статус: локальная двухрежимная реализация завершена двумя логическими коммитами; производственное переключение не выполнялось.
- Область: исходный код и локальная документация Program-Loyal, локальная копия проекта развёртывания webhook_03, официальная спецификация iiko Cloud API.
- Ограничение: подключения к рабочим серверам и изменяющие запросы во внешние системы не выполнялись.

## 1. Краткий итог

До текущей реализации проект использовал iiko Cloud API и зависел от старой авторизации через поле `apiLogin`.

Старая авторизация была реализована независимо в трёх клиентах:

1. guests/services/iiko_client.py;
2. guests/services/iiko_coupon_client.py;
3. guests/services/iiko_customer_category_client.py.

В исходном состоянии во всех трёх случаях значение настройки `IIKO_API_KEY` передавалось как `apiLogin`. Поэтому старое значение нельзя переносить в новый параметр `apiKey`. В реализованной схеме реквизиты разделены на `IIKO_LEGACY_API_LOGIN` и новый `IIKO_API_KEY`.

От старой авторизации зависят:

1. поиск и восстановление гостя по телефону;
2. обработка части вебхуков посещений, категорий и баланса;
3. добавление и снятие категории iikoCard «Активный купон SAGUR»;
4. проверка загруженных в iikoCard купонных пулов;
5. восстановление отсутствующего локально гостя в части контрольного OLAP-контура.

Отдельная интеграция с iikoServer использует /resto/api/auth и не относится к рассматриваемому переходу.

Официальная спецификация на дату анализа:

1. помечает POST /api/1/access_token устаревшим;
2. определяет POST /api/v2/access_token как новую точку авторизации;
3. требует appId, clientSecret и apiKey;
4. возвращает token и correlationId;
5. определяет token как JWT со сроком действия один час и полем exp;
6. не переносит рабочие методы из /api/1.

Источник: https://api-ru.iiko.services/api-docs/docs

Точная дата отключения старой точки в доступной спецификации не указана. Подтверждён статус устаревшего метода, но не срок его окончательного удаления.

Переход необходим для сохранения перечисленных функций после отключения старой авторизации.

По решению владельца для выпуска выбрана временная двухрежимная схема: один образ поддерживает `legacy` и `v2`, а активный способ задаётся обязательной переменной окружения. Автоматический возврат с `v2` на `legacy` запрещён. После подтверждённой стабильной работы `v2` старый режим удаляется отдельным изменением кода.

## 3. Разделение интеграций

### 3.1 iiko Cloud API

Определяющий адрес: api-ru.iiko.services.

Используется для:

1. получения Bearer-токена;
2. поиска гостя;
3. чтения сведений о купонах;
4. добавления и снятия категории гостя.

Именно эта область требует перехода на авторизацию версии 2.

### 3.2 iikoServer API

Определяющий адрес: базовый URL вида /resto/api.

Используется для:

1. POST /resto/api/auth;
2. POST /resto/api/v2/reports/olap;
3. загрузки OLAP-данных по заказам, номенклатуре, телефонам и купонам.

Авторизация выполняется логином и хешем пароля. Оснований относить её к изменению iiko Cloud API нет.

### 3.3 iikoCard

iikoCard в проекте является функциональной областью лояльности: купоны, гости и категории. Само название iikoCard не определяет способ авторизации. В исследуемом проекте соответствующие исходящие методы вызываются через iiko Cloud API.

### 3.4 iikoChain и OLAP

Номенклатура, заказы и факты применения купонов поступают через iikoServer OLAP. Вызовов облачных методов организаций, номенклатуры или заказов не найдено.

### 3.5 API САГУР

Фоновая обработка получает исходные вебхуки через API САГУР. Это отдельная авторизация. Внутри обработки некоторых событий выполняется дополнительный поиск гостя через iiko Cloud API.

## 4. Фактические цепочки взаимодействия

### 4.1 Восстановление гостя из iikoCard

Цепочка:

    worker-bonus или задача Django Q
    → получение ожидающих вебхуков через API САГУР
    → handle_api_webhook
    → событие notificationType=1, notificationType=5 или событие баланса
    → гость не найден локально, но присутствует телефон
    → get_or_create_guest_from_iiko
    → IikoClient.get_customer_by_phone
    → получение токена через apiLogin
    → POST customer/info
    → создание или обновление Guest
    → обновление VisitHistory, категории либо постановка уведомления

Доказательства достижимости:

1. loyalty_viewer/settings.py:160-179 регистрирует sync_webhooks_recent каждые десять минут;
2. guests/tasks.py:25-40 вызывает process_recent_webhooks;
3. guests/services/webhooks.py:744-817 маршрутизирует типы событий;
4. guests/services/webhooks.py:234-294 выполняет восстановление гостя;
5. production Compose запускает отдельный run_webhook_worker.

Условие обращения к iiko Cloud: локальный гость не найден, но в событии есть телефон. Для уже известного гостя внешний поиск не требуется.

Результат customer/info используется для создания или обновления Guest. Далее:

1. notificationType=1 обновляет VisitHistory;
2. notificationType=5 назначает локальную категорию;
3. событие баланса создаёт уведомление через общий контур задач.

### 4.2 Добавление категории iikoCard

Цепочка:

    назначение купона разовой кампанией или автосценарием

    → получение токена через apiLogin
    → POST customer_category/add
    → событие ACKED
    → статус назначения iiko_category_add_status=ok
    → при включённом gate разрешение отправки купонного сообщения

Основные места:

1. guests/services/coupon_campaign.py:445-502;
2. guests/services/coupon_autoscenarios.py:1478-1482;
3. guests/services/iiko_customer_category_sync.py:190-252;
4. guests/services/iiko_customer_category_sync.py:401-524;
5. guests/tasks.py:172-211;
6. loyalty_viewer/settings.py:1315-1321.

Плановая задача регистрируется только при одновременном включении:

1. IIKO_CUSTOMER_CATEGORY_SYNC_ENABLED;

### 4.3 Снятие категории iikoCard

Цепочка:

    отмена, истечение или использование назначения купона

    → enqueue_iiko_category_remove_if_last_coupon
    → событие remove
    → повторная защитная проверка в worker
    → получение токена через apiLogin

Точки формирования:

1. guests/services/coupon_campaign_lifecycle.py:188-196 и 317-325;
2. guests/services/coupon_redemption_sync.py:314-322;

Если старая авторизация перестанет работать, очередь remove будет переходить в ошибки. Категория может остаться у гостя и влиять на правила применения будущих акций.

### 6.1 Неоднозначность базового URL

Купонный и категорийный клиенты добавляют /api/1 к корневому URL. Общий IikoClient этого не делает.

Если буквально применить .env.sample, общий клиент построит:

1. https://api-ru.iiko.services/access_token;
2. https://api-ru.iiko.services/loyalty/iiko/customer/info.

Такие адреса не соответствуют официальной спецификации. Если в рабочем окружении IIKO_API_BASE_URL уже содержит /api/1, общий клиент построит правильные адреса. Фактическое значение рабочей переменной не проверено.

### 6.2 Фактический смысл IIKO_API_KEY

В каждом облачном клиенте значение переменной сериализуется в поле apiLogin. Следовательно:

1. код предполагает старый реквизит;
2. имя переменной вводит в заблуждение;
3. фактическое секретное значение не выводилось;
4. перенос значения в новый apiKey без внешнего подтверждения запрещён.

## 9. Технические недостатки исходной авторизации

1. Три независимые реализации получения токена.
2. Кэширование на фиксированные 14 минут без чтения exp.
3. Нет потокобезопасной блокировки обновления.
4. Нет защиты от одновременного массового обновления токена.
5. Нет очистки токена и однократного повторного запроса после HTTP 401.
6. Нет единой политики HTTP 408, 429 и 5xx.
7. Разбор JSON местами не защищён от некорректного ответа.
8. Тело ответа внешнего сервиса местами включается в исключения и журналы.
9. correlationId не сохраняется.
10. Глобальный IikoClient создаётся при импорте и зависит от корректности IIKO_API_BASE_URL.
11. Тесты общего клиента не проверяют официальные полные URL.

## 10. Оценка влияния отключения старой точки

| Область | Последствие |
|---|---|
| Приложение целиком | Не должно остановиться |
| Новые купонные назначения при обязательном iikoCard-gate | Могут полностью перестать переходить к отправке |
| Добавление категории | Новые add-события будут ошибочными до исчерпания повторов |
| Снятие категории | Remove не выполнится; категория может остаться у гостя |
| Уже известные локальные гости | Основная обработка вебхуков продолжится без внешнего поиска |
| Неизвестные локально гости | Не будут созданы из iikoCard |
| Баланс и посещения | Нарушатся только сценарии, которым требуется восстановление гостя |
| Проверка купонных пулов | Пользовательская кнопка и команда завершатся ошибкой |
| iikoServer OLAP | Продолжит работать |
| Контрольный OLAP pull | OLAP-запрос продолжится, но условный поиск неизвестного гостя не сработает |
| Ранее подтверждённые данные | Не изменятся задним числом |

## 11. Целевой конфигурационный контракт

Предлагаемые переменные:

    IIKO_AUTH_MODE=legacy|v2
    IIKO_LEGACY_API_LOGIN
    IIKO_LEGACY_AUTH_URL=https://api-ru.iiko.services/api/1/access_token
    IIKO_APP_ID
    IIKO_CLIENT_SECRET
    IIKO_API_KEY
    IIKO_AUTH_URL=https://api-ru.iiko.services/api/v2/access_token
    IIKO_API_BASE_URL=https://api-ru.iiko.services/api/1
    IIKO_ORGANIZATION_ID

Факт текущего проекта: `settings.py` только читает основные параметры iiko и не останавливает запуск Django при их отсутствии. Проверки уже существуют локально: команда проверки купонов проверяет три параметра при своём запуске, а служба синхронизации категорий проверяет их в `from_settings()` при создании этой службы. Общий клиент поиска гостя не имеет единой предварительной проверки и обрабатывает проблему в своём текущем вызывающем контуре.

Целевое поведение сохраняет эту границу. Новая глобальная проверка при запуске приложения не добавляется. Правило «при неполном наборе шлюз молча не создаётся» не вводится. Ошибка конфигурации обнаруживается и сообщается только при создании или использовании соответствующего клиента, службы или команды iiko — в тех же прикладных точках, где это происходит сейчас.

Правила:

1. `IIKO_AUTH_MODE` читается без глобальной проверки запуска; при фактическом создании поставщика токена он обязан иметь значение `legacy` или `v2`, неявного режима по умолчанию нет;
2. текущее старое значение сначала переименовывается во внешнем хранилище в `IIKO_LEGACY_API_LOGIN`;
3. новый `IIKO_API_KEY` создаётся отдельно в iikoWeb;
4. старое значение нельзя автоматически использовать как новый `apiKey`;
5. в режиме `legacy` обязательны только старые реквизиты, в режиме `v2` — `IIKO_APP_ID`, `IIKO_CLIENT_SECRET` и новый `IIKO_API_KEY`;
6. частичная конфигурация активного режима является локальной ошибкой соответствующей операции iiko, а не причиной остановки всего приложения и не основанием молча пропустить создание клиента;
7. ошибка `v2` не вызывает автоматического запроса через `legacy`;
8. значения секретов не сохраняются в репозитории, документации, тестовых данных и журналах;
9. адреса старой и новой авторизации отделены от `IIKO_API_BASE_URL`;
10. рабочие методы в обоих режимах всегда используют `IIKO_API_BASE_URL` с `/api/1`.

## 12. Выбор способа переключения

Рассмотрены два варианта.

### 12.1 Прямой переход

Преимущества:

1. один целевой контракт;
2. нет риска перепутать apiLogin и apiKey во время выполнения;
3. меньше ветвей кода и тестов;
4. старый механизм удаляется сразу после стабилизации.

Недостаток: откат приложения требует временно сохранённого старого секрета и доступности старой точки.

### 12.2 Временный переключатель legacy/v2

Преимущества:

1. один и тот же проверенный образ можно сначала запустить с прежней авторизацией, а затем переключить на `v2`;
2. при дефекте новой авторизации можно вручную вернуть `legacy` без замены образа;
3. изменение способа авторизации отделяется от изменения прикладного кода.

Недостатки:

1. хранение двух наборов секретов;
2. риск неправильного выбора режима;
3. удвоение тестовых сценариев;
4. сохранение устаревшего кода;
5. переключатель бесполезен после отключения старой точки.

### 12.3 Утверждённое решение

Выбрана временная двухрежимная схема. Это не параллельная отправка двух запросов и не автоматический запасной путь. В каждый момент процесс использует только режим, явно заданный через `IIKO_AUTH_MODE`.

Последовательность:

1. развернуть двухрежимный образ с `IIKO_AUTH_MODE=legacy` и подтвердить отсутствие регрессии;
2. проверить `v2` в изолированном тестовом окружении;
3. вручную переключить все производственные процессы на `IIKO_AUTH_MODE=v2`;
4. сохранить `legacy` только на согласованный период стабилизации и только пока старая точка доступна;
5. отдельным изменением удалить старый режим, его тесты и секрет.

Автоматический переход с `v2` на `legacy` запрещён: он скрывал бы ошибки новых реквизитов и мог бы незаметно оставить систему на устаревшей авторизации.

## 14. Откат и аварийные действия

### 14.1 Условия начала отката

1. стабильная невозможность получить токен версии 2;
2. новый ключ не видит нужные организации;
3. растёт очередь ошибочных add/remove;
4. купонные сообщения блокируются gate;
5. нарушен поиск неизвестных гостей;
6. не работает операторская проверка купонных пулов;
7. обнаружено попадание секрета или JWT в журнал.

### 14.2 Порядок отката

1. остановить дальнейшее развёртывание;
2. явно установить `IIKO_AUTH_MODE=legacy`;
3. пересоздать все процессы Program-Loyal на том же двухрежимном образе;
4. проверить доступность старой точки;
5. проверить очередь категорий и обработку вебхуков;
6. если дефект не ограничен стратегией `v2`, вернуть предыдущий образ и прежнюю настройку только из защищённого хранилища;
7. не очищать ошибочные события до установления причины.

После официального отключения `/api/1/access_token` ни переключение на `legacy`, ни возврат предыдущего образа не восстановят работу.

### 14.3 Компрометация clientSecret

1. перевыпустить clientSecret в портале разработчика;
2. считать предыдущий секрет отозванным;
3. обновить секрет во всех окружениях;
4. перезапустить процессы;
5. подтвердить получение нового токена;
6. проверить журналы на отсутствие раскрытия.

### 14.4 Данные для технической поддержки

1. correlationId;
2. время запроса;
3. HTTP-метод и адрес без секретов;
4. HTTP-статус;
5. имя процесса и сценарий;
6. версия приложения и коммит;
7. идентификатор организации;
8. номер попытки;
9. безопасный код внешней ошибки;
10. отсутствие в обращении clientSecret, apiKey, apiLogin и JWT.

## 15. Критерии готовности

### 15.1 Критерии производственного переключения на v2

1. все процессы явно работают с `IIKO_AUTH_MODE=v2`;
2. в производственной диагностике не вызывается `/api/1/access_token`;
3. `token` получается через `/api/v2/access_token`;
4. рабочие методы продолжают использовать `/api/1`;
5. проверены поиск гостя, купоны и категории;
6. HTTP 401 приводит максимум к одной повторной авторизации в `v2`, без вызова `legacy`;
7. конкурентное обновление не создаёт лавину запросов;
8. тесты обоих режимов проходят;
9. секреты и JWT отсутствуют в коде, тестовых данных и журналах;
10. `correlationId` доступен диагностике;
11. мониторинг ошибок авторизации определён.

### 15.2 Критерии полного завершения миграции

1. период стабилизации `v2` завершён отдельным решением владельца;
2. стратегия `legacy`, `apiLogin` и `/api/1/access_token` отсутствуют в выполняемом коде;
3. переключатель `IIKO_AUTH_MODE` удалён как ненужный;
4. старый секрет удалён из всех хранилищ;
5. статическая проверка запрещает возврат старой точки;
6. документация описывает только действующий режим `v2`.

## 17. Результат локальной реализации и граница выпуска

Реализация зафиксирована логическими коммитами:

1. `5ce9834e` — «Добавить двухрежимную авторизацию iiko Cloud API»;
2. `2c910e2` — «Перевести клиенты iiko на общий транспорт».

Подтверждено локально:

1. 16 тестов поставщика токена и `.env.sample` прошли;
2. 63 связанных теста транспорта, трёх клиентов, купонов, категорий и воркера прошли;
3. 69 смежных тестов баланса, журналирования и webhook-контура прошли;
4. полный набор выполнил 1019 тестов: 1011 прошли, 8 завершились ошибкой;
5. те же восемь ошибок в точности воспроизведены на родительском коммите `6977fb8` до миграции iiko: семь относятся к исходным данным и валидации сценариев уведомлений, одна — к сериализации `Decimal` в существующем JSON-отчёте;
6. следовательно, коммиты миграции iiko не внесли новых отказов в полном наборе, однако общий набор проекта пока не является полностью зелёным;
7. `manage.py check` не выявил замечаний;
8. `apiLogin` и `/api/1/access_token` остались только в изолированной стратегии `legacy`;
9. прикладные клиенты используют общий транспорт и рабочий префикс `/api/1`;
10. новая глобальная проверка запуска Django не добавлена;
11. HTTP 401 вызывает ровно одно обновление токена без автоматического перехода между `v2` и `legacy`;
12. немедленные повторы `add/remove` после неопределённого сетевого исхода отключены.

Не выполнено и не считается подтверждённым:

1. полностью зелёный общий набор тестов проекта: остаются восемь доказанно исходных отказов вне контура миграции iiko;
2. read-only доступ рабочего токена к требуемой организации и рабочим методам `/api/1`;
3. изолированное развёртывание Docker Compose;
4. производственное развёртывание образа в режиме `legacy`;
5. производственное переключение на `v2`;
6. период наблюдения, ручной откат и последующее удаление `legacy`;
7. любые внешние изменяющие запросы.

Следующий минимальный шаг до выпуска: подготовить изолированную проверку одного образа в режимах `legacy` и `v2`. Восемь исходных отказов общего набора следует устранить отдельной задачей, не смешивая её с миграцией авторизации.
