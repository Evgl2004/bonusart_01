# Дорожная карта: разовая текстовая рассылка по отбору гостей

Дата: 2026-06-19  
Статус: рабочая дорожная карта реализации

## 1. Цель

Довести до рабочего состояния связку:

`Гости -> отбор аудитории -> проверка возможности доставки -> черновик разовой рассылки -> запуск обычной рассылки`.

Первый практический запрос маркетологов:

1. выбрать гостей, которые связаны с заведением `Сами Сусами`;
2. учитывать только гостей, которым можно отправить сообщение через новые боты Telegram/ВК/Макс;
3. создать обычную текстовую рассылку без купонов;
4. перед запуском видеть понятный расчет аудитории.

## 2. Что уже есть в проекте

1. Обычная рассылка хранится в `Mailing`.
2. Строки аудитории обычной рассылки хранятся в `MailingGuest`.
3. Доставка идет через общий контур `MailingGuest -> DispatchTask`.
4. Рабочий экран гостей уже умеет создавать черновик рассылки по текущему отбору.
5. Сохраненные отборы гостей уже представлены моделью `GuestWorkbenchFilterPreset`.

## 3. Проблемы текущего состояния

1. Черновик рассылки из экрана гостей создается только по строкам, показанным на странице.
2. Сейчас действует ограничение быстрого списка: по умолчанию 200 гостей.
3. Для массовой рассылки это ограничение должно быть управляемым:
   - если включен лимит, использовать указанное значение;
   - если лимит выключен, создавать аудиторию по всему отбору.
4. Для отбора по заведению не хватает отдельной понятной стратегии.
5. Перед созданием рассылки не хватает нормальной проверки:
   - сколько гостей найдено по условию;
   - сколько имеет активную привязку к выбранным ботам;
   - сколько имеет разрешение на сообщения;
   - сколько будет добавлено в аудиторию;
   - сколько будет пропущено и почему.

## 4. Способы связи гостя с заведением

Для обычного отбора гостей используем те же бизнес-смыслы, которые уже применяются в купонных автосценариях:

1. `Был хотя бы 1 раз`  
   Гость попадет в отбор, если у него есть хотя бы один заказ/визит в выбранном заведении.

2. `Любимое заведение`  
   Гость попадет в отбор, если выбранное заведение является заведением с максимальным числом заказов среди всех заведений гостя. При равенстве выбирается более свежий визит.

3. `Самое последнее посещение`  
   Гость попадет в отбор, если последнее известное посещение/заказ гостя относится к выбранному заведению.

## 5. Источник данных

Основной источник для отбора по заведению:

1. `GuestRestaurantDailyOrderFact` - быстрый дневной слой по гостю и заведению.
2. `OrderFact` - детальный слой чеков; использовать как источник для уточнения, если дневного слоя недостаточно.

Для первой реализации целимся в дневной слой, потому что он уже предназначен для быстрых маркетинговых отборов.

## 6. Предлагаемый поток пользователя

1. Пользователь открывает раздел `Гости`.
2. Настраивает отбор:
   - заведение;
   - способ связи гостя с заведением;
   - период посещений;
   - дополнительные условия, если нужны.
3. Нажимает `Проверить для рассылки`.
4. Система показывает расчет аудитории.
5. Пользователь выбирает:
   - шаблон сообщения;
   - ботов;
   - режим отправки;
   - окно отправки;
   - лимит аудитории или без лимита.
6. Пользователь создает черновик рассылки.
7. Дальше работает обычный контур рассылок.

## 7. Этапы реализации

### Этап 1. Документация и фиксация решения

Результат:

1. Дорожная карта сохранена.
2. Проверено, что три способа выбора заведения уже есть в купонных автосценариях.

Точка коммита:

1. Отдельный коммит документации после подтверждения.

### Этап 2. Сервис отбора гостей по заведению

Результат:

1. Добавлен единый сервис, который возвращает гостей по выбранному заведению и режиму:
   - был хотя бы 1 раз;
   - любимое заведение;
   - самое последнее посещение.
2. Сервис умеет считать весь отбор без ограничения интерфейсной таблицы.
3. Сервис умеет применять лимит только когда он явно включен.
4. Сервис возвращает диагностические счетчики.

Точка коммита:

1. Сервис и тесты сервиса.

### Этап 3. Проверка доставки перед созданием рассылки

Результат:

1. Добавлен расчет доступности отправки:
   - есть активная привязка к выбранному боту;
   - есть разрешение на сообщения;
   - не стоит запрет отправки;
   - заполнен внешний идентификатор чата/пользователя.
2. Пользователь видит не только общее число гостей, но и реальные доступные к отправке строки.

Точка коммита:

1. Проверка доставки и тесты.

### Этап 4. Разделение аудитории по новым ботам и legacy Telegram-гостям

Результат:

1. В фильтрах рабочего экрана гостей добавлен тип аудитории:
   - все гости;
   - гости, которым доступна рассылка через новые боты Telegram/ВК/Макс;
   - legacy Telegram-гости: старый канал того же физического Telegram-бота есть, новой регистрации в `GuestBotBinding` нет;
   - гости в новых ботах, которым сейчас нельзя отправлять сообщения из-за отсутствия согласия или запрета отправки.
2. Фильтр влияет на карточки, сегменты, таблицу гостей и создание черновика.
3. Для legacy Telegram-гостей обычная рассылка создаёт задачу доставки через выбранный Telegram-бот и `external_id` из `VtelemaxRecipientChannel`; гости с новой привязкой, но запретом отправки, в этот fallback не попадают.
4. Сохраненные пресеты запоминают выбранный тип аудитории.

Точка коммита:

1. Фильтр аудитории, миграция пресетов и тесты.

### Этап 5. Создание черновика обычной рассылки по полному отбору

Результат:

1. Черновик `Mailing` создается с выбранным шаблоном, ботами, режимом отправки и окном отправки.
2. Строки `MailingGuest` создаются по всей подтвержденной аудитории.
3. Ограничение 200 строк больше не блокирует массовый отбор.
4. Если включен лимит, применяется указанное значение.

Точка коммита:

1. Создание черновика и тесты.

### Этап 6. Интерфейс

Результат:

1. На экране `Гости` добавлены понятные элементы для:
   - способа связи гостя с заведением;
   - периода посещений;
   - лимита аудитории;
   - проверки аудитории;
   - создания черновика.
2. Текущие отборы и сохраненные пресеты не ломаются.

Точка коммита:

1. Интерфейс и тесты представлений.

## 8. Что не делаем в первом этапе

1. Не создаем новую систему рассылок.
2. Не создаем новый автосценарий.
3. Не смешиваем этот контур с купонными автосценариями.
4. Не запускаем рассылку сразу после создания черновика.
5. Не отправляем сообщения гостям без явного подтверждения пользователя.

## 9. Проверки готовности

1. Отбор `Сами Сусами + был хотя бы 1 раз` возвращает ожидаемую аудиторию.
2. Отбор `Сами Сусами + любимое заведение` возвращает только гостей, для которых это заведение является основным по числу заказов.
3. Отбор `Сами Сусами + самое последнее посещение` возвращает только гостей, у которых последнее посещение относится к этому заведению.
4. Черновик обычной рассылки создается без купонов.
5. Строки `MailingGuest` создаются только для гостей, доступных к отправке.
6. Созданная рассылка остается выключенной до ручного запуска.
