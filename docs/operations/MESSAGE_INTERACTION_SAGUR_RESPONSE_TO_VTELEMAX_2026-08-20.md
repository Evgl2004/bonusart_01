# Технический ответ SAGUR команде vtelemax по интерактивным сообщениям

- Дата: 2026-08-20.
- Основание: `SAGUR_MESSAGE_INTERACTIONS_TECHNICAL_RESPONSE_2026-08-20.md` и приложенные протоколы живых испытаний Telegram, VK и MAX.
- Статус: передан и письменно принят командой vtelemax 2026-08-20; дополнительных технических противоречий не заявлено.

## 1. Общий итог

SAGUR принимает результаты живых испытаний vtelemax и подтверждает техническую реализуемость обработки интерактивных кнопок на Telegram, VK и MAX в заявленных границах.

Подтверждёнными считаем следующие факты:

1. служебный JSON версии 1 возвращается в vtelemax без изменения на всех трёх платформах;
2. для текстового сообщения с набором `l+d / m` на всех трёх платформах можно удалить `l/d`, сохранить кликабельную `m`, текст и исходное сообщение;
3. два последовательных реальных нажатия сохранённой `m` на каждой платформе получили разные платформенные идентификаторы;
4. техническая повторная доставка одного события с новым платформенным идентификатором не воспроизводилась и не может считаться распознаваемой гарантированно;
5. рабочие таблицы, обработчики, пакетный отправитель и передача событий в SAGUR ещё не реализованы.

Предложенное изменение служебного JSON согласовано в уточнённом ниже виде.

Этот ответ закрывает техническое согласование контракта. Он не является разрешением владельца проекта на начало прикладной разработки: такое разрешение будет передано отдельно после завершения текущего обсуждения.

## 2. Утверждённая версия 2 служебного JSON кнопки

Для новых сообщений утверждён формат:

```json
{"t":"si","v":2,"i":123456,"a":"ldm"}
```

Правила поля `a`:

1. первый символ — фактически нажатое действие;
2. вся строка — семантический состав исходного набора;
3. нажатое действие помещается первым, остальные действия следуют в исходном порядке;
4. допускается только закрытый перечень значений.

| Исходный набор | Нажатое действие | `a` |
|---|---|---|
| `l,d,m` | `l` | `ldm` |
| `l,d,m` | `d` | `dlm` |
| `l,d,m` | `m` | `mld` |
| `l,d,c` | `l` | `ldc` |
| `l,d,c` | `d` | `dlc` |
| `l,d,c` | `c` | `cld` |

Произвольные перестановки, повторяющиеся символы, неизвестные действия и другие комбинации должны отклоняться.

Обязательные проверки версии 2:

- `t` строго равно `si`;
- `v` строго равно целому числу `2`;
- `i` является положительным 64-битным идентификатором интерактивности SAGUR;
- `a` принадлежит закрытому перечню;
- неизвестные атрибуты отклоняются;
- фактическая сериализация выполняется в UTF-8 без необязательных пробелов и без дополнительного кодирования.

Проверенный расчёт размера:

- пример с `i=123456` занимает 37 байт;
- вариант с максимальным положительным 64-битным `i` занимает 50 байт;
- до ограничения Telegram 64 байта остаётся 14 байт.

После разбора vtelemax использует первый символ `a` как одиночное действие. В пакетном событии для SAGUR передаётся только `l`, `d`, `m` или `c`; составная строка туда не переносится. Версия пакетного контракта vtelemax → SAGUR остаётся равной 1.

## 3. Совместимость версии 1

Версия 1 остаётся обязательной для бессрочной обработки ранее отправленных сообщений:

```json
{"t":"si","v":1,"i":123456,"a":"l"}
```

После согласованного включения версии 2 SAGUR не создаёт новые кнопки версии 1. vtelemax продолжает принимать версию 1 без ограничения срока, поскольку кнопки ранее отправленных сообщений не имеют срока действия.

Порядок включения:

1. vtelemax развёртывает совместимый разбор версий 1 и 2;
2. проходят строгие положительные и отрицательные тесты всех шести значений версии 2;
3. команда vtelemax подтверждает готовность разбора;
4. только после этого SAGUR начинает формировать версию 2.

Одностороннее включение версии 2 любой из сторон запрещено.

## 4. Изменение фактической клавиатуры

Составное поле `a` передаёт семантический состав набора, но не заменяет фактическую платформенную структуру сообщения.

При удалении оценок vtelemax обязан:

1. получить фактическое исходное сообщение или клавиатуру;
2. удалить только кнопки `l/d` соответствующей интерактивности;
3. сохранить реальные подписи, эмодзи, ряды, поддерживаемые стили и остальные кнопки;
4. сохранить текст, разметку и остальные вложения сообщения;
5. не создавать дублирующее сообщение.

Строить визуальную клавиатуру заново только по составной строке `a` нельзя. Если получить или безопасно изменить фактическую структуру невозможно, нельзя угадывать кнопку, удалять всю клавиатуру или уничтожать допустимую навигацию. Ошибка пользовательского действия фиксируется отдельно от состояния доставки события в SAGUR.

## 5. Платформенные повторы и уникальность событий

SAGUR принимает уточнённую гарантию vtelemax:

1. локальная уникальность обеспечивается сочетанием `platform + bot_scope + platform_callback_id`;
2. повтор с тем же сочетанием не создаёт вторую строку и новый `event_id`;
3. новый платформенный идентификатор создаёт новое локальное событие и новый `event_id`;
4. все HTTP-повторы доставки одной локальной строки используют прежний `event_id`;
5. если технический повтор платформы придёт с новым идентификатором, достоверно отличить его от нового реального нажатия невозможно.

В последней неопределённости принимается приоритет недопущения потери реального нажатия: новый платформенный идентификатор считается новым событием. Это ограничение должно быть отражено в коде, тестах и эксплуатационной документации и не должно описываться как полная защита от любого возможного платформенного повтора.

## 6. Утверждённый смысл `occurred_at`

`occurred_at` — серверное время, когда vtelemax впервые получил обратный вызов платформы и успешно сохранил его в надёжном хранилище.

Это значение:

- не является временем физического касания экрана;
- не берётся из часов телефона пользователя;
- не является временем пакетной отправки;
- не является временем приёма события SAGUR;
- создаётся один раз при первой успешной локальной вставке;
- не меняется при повторных HTTP-попытках доставки того же `event_id`.

## 7. Распределение ответственности

Подтверждаем ранее согласованное разделение:

- vtelemax сохраняет и передаёт каждое реально полученное действие `l`, `d`, `m` или `c`;
- vtelemax не выбирает первую оценку и не отбрасывает последующие реальные `l/d`;
- SAGUR транзакционно определяет первую принятую оценку;
- последующие реальные оценки сохраняются в SAGUR с результатом `rating_already_recorded`;
- каждое новое реальное нажатие `m/c` сохраняется и учитывается отдельно;
- повторная HTTP-доставка прежнего `event_id` не создаёт новое событие SAGUR.

## 8. Локальное хранение vtelemax

SAGUR не возражает против использования в первой реализации одной таблицы PostgreSQL для неизменяемого факта нажатия и изменяемого состояния его доставки в SAGUR при соблюдении заявленных условий:

- факт и постановка в доставку создаются одной атомарной вставкой;
- поля факта после вставки не меняются;
- состояние пользовательского действия отделено от состояния доставки;
- активная очередь выбирается через частичные индексы;
- внешний HTTP-запрос не выполняется внутри длительной транзакции базы;
- завершённые события автоматически не удаляются;
- глубина очереди, возраст старейшего события, повторы, просроченные блокировки и размер таблицы наблюдаются.

Это внутреннее решение vtelemax и оно не изменяет утверждённую модель хранения SAGUR.

## 9. Пакетная доставка и HMAC

Подтверждаем пакетный контракт версии 1:

- от 1 до 100 событий;
- не более 65 536 байт тела;
- рабочее окно накопления около пяти минут;
- новый `request_id` для каждой HTTP-попытки;
- неизменный `event_id` для повторной доставки одного события;
- поэлементный частичный результат;
- временные транспортные ошибки повторяются;
- подтверждённые элементы повторно не отправляются;
- постоянный поэлементный отказ переводит запись в диагностируемое состояние и не удаляет её.

Окончательно подтверждёнными считаются `accepted`, `duplicate` и `rating_already_recorded`. Отсутствующий поэлементный результат не является подтверждением.

До совместного включения стороны обязаны использовать одну общую байтовую фикстуру HMAC, подтверждающую полное совпадение:

- метода;
- пути;
- отметки времени;
- фактических байтов тела;
- SHA-256 тела;
- канонической строки;
- итоговой подписи.

## 10. Оставшиеся приёмочные проверки

Подтверждение текстового сценария `l+d / m` на трёх платформах принято. До выпуска функции остаются обязательными:

1. строгие тесты версии 2 и совместимости версии 1;
2. набор `l+d / c` и рабочее открытие общего раздела купонов;
3. сохранность фактических вложений и разметки используемых шаблонов;
4. полная доставка пакета vtelemax → SAGUR с частичными результатами и повторами;
5. общая байтовая проверка HMAC;
6. нагрузочная проверка утверждённой таблицы и частичных индексов;
7. совместная сквозная проверка Telegram, VK и MAX.

Переход MAX с `platform-api.max.ru` на `platform-api2.max.ru` остаётся отдельной эксплуатационной задачей, связанной с доверенной цепочкой сертификата. Он не меняет согласованную структуру кнопок, но должен быть закрыт до соответствующего производственного перехода.

Дополнительных архитектурных вопросов к команде vtelemax у SAGUR нет.

Просим подтвердить получение и зафиксировать в документации vtelemax:

1. согласование версии 2 и закрытого перечня `ldm/dlm/mld/ldc/dlc/cld`;
2. бессрочную совместимость версии 1;
3. передачу в пакет SAGUR только одиночного действия;
4. утверждённый смысл `occurred_at`;
5. границу гарантии по платформенным повторам;
6. запрет восстанавливать визуальную клавиатуру вслепую только из составного `a`.
