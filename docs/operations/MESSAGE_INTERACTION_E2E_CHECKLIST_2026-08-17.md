# Сквозная проверка интерактивных сообщений SAGUR и vtelemax

- Дата: 2026-08-17.
- Статус: обязательный протокол приёмки первой версии.
- Основания: реестр решений, окончательный контракт и обе дорожные карты от 2026-08-17.

## 1. Правило прохождения

Проверка выполняется последовательно: автоматические тесты, прямые запросы между системами, тестовые боты, затем одна ограниченная боевая рассылка после ручного разрешения владельца проекта.

Для каждого пункта сохраняются:

- среда, дата и версии сборок SAGUR и vtelemax;
- платформа и бот без публикации секретов;
- `DispatchTask.id`, `interaction_id`, `event_id` и `request_id`, если применимо;
- ожидаемый и фактический результат;
- безопасная выдержка журнала или снимок интерфейса;
- итог «пройдено», «не пройдено» либо «не применимо» с причиной.

Ни один результат не называется прочтением. Кнопка подтверждает только взаимодействие.

## 2. Условия до начала

- [ ] Все пять проектных документов находятся под контролем версий и не противоречат друг другу.
- [ ] Реализация SAGUR и vtelemax ссылается на версию контракта 1.
- [ ] Автоматические тесты обоих проектов пройдены.
- [ ] Миграции проверены на PostgreSQL и тестовом SQLite, где он используется.
- [ ] Контейнер `migrate-bonus` успешно запущен повторно без создания дублей.
- [ ] В SAGUR создание новых кнопок выключено по умолчанию.
- [ ] Защищённая точка SAGUR включается отдельно от создания кнопок.
- [ ] vtelemax сохраняет нажатие до попытки HTTP-доставки.
- [ ] Тестовые боты SAGUR и vtelemax совпадают для Telegram, VK и MAX.
- [ ] Системные часы обеих сред синхронизированы.
- [ ] Специализированный или общий HMAC-секрет совпадает, но нигде не выведен.
- [ ] Назначены ответственные за SAGUR, vtelemax и итоговое решение о пилоте.

Запрещено начинать боевой тест только потому, что тестовая среда прошла автоматически. Разрешение и выбор одной безопасной рассылки фиксируются вручную в рабочем диалоге.

## 3. Проверка схемы и миграций SAGUR

### 3.1. Чистая и текущая база

- [ ] На чистой базе создаются только `MessageInteraction` и `MessageInteractionEvent`.
- [ ] На текущей базе миграция не меняет смысл и работу существующих `DispatchTask`.
- [ ] Для существующих сообщений задним числом интерактивности не создаются.
- [ ] Повторный `migrate` ничего не дублирует.
- [ ] Повторный запуск `migrate-bonus` ничего не дублирует.

### 3.2. Частично созданная схема

- [ ] Отсутствующая совместимая часть создаётся.
- [ ] Уже существующая совместимая часть проверяется и не дублируется.
- [ ] Несовместимый столбец, индекс или ограничение даёт понятную блокирующую ошибку.
- [ ] Миграция не объявляет успех при несовместимой структуре.

### 3.3. Ограничения данных

- [ ] `dispatch_task_id` уникален и защищён от удаления через `PROTECT`.
- [ ] `event_id` уникален.
- [ ] Первая принятая `l` либо `d` на одну интерактивность единственна на уровне базы.
- [ ] `rating_already_recorded` невозможно сохранить для `c` или `m`.
- [ ] Неверные коды набора, действия и результата отклоняются.
- [ ] Нет таблиц отдельных кнопок и входящих пакетов.

## 4. Контракт без мессенджеров

Прямые запросы выполняются из временного файла со скриптом внутри серверного контейнера или штатной диагностической командой. Новые пакеты для этого не устанавливаются. Секрет читается из настроек среды и не печатается.

Проверяемая точка:

```text
POST /internal/integration/v1/vtelemax/message-interactions/events
```

### 4.1. Совпадение подписи

- [ ] Одинаковая фиксированная строка JSON даёт одинаковый SHA-256 на обеих сторонах.
- [ ] Одинаковая строка `POST\nпуть\nвремя\nSHA256(тела)` даёт одинаковый HMAC-SHA256.
- [ ] Изменение одного байта тела без пересчёта подписи даёт HTTP 401.
- [ ] Изменение пути, метода или времени без пересчёта подписи даёт HTTP 401.
- [ ] Сравнение подписи выполняется постоянным по времени способом.

### 4.2. Оболочка запроса

- [ ] `Content-Type: application/json` принимается.
- [ ] Параметр кодировки у `Content-Type` обрабатывается по контракту.
- [ ] Неверный тип даёт 415.
- [ ] Не POST даёт 405 и `Allow: POST`.
- [ ] Не-HTTPS при обязательном HTTPS даёт 403.
- [ ] Тело более 65 536 байт даёт 413 до бизнес-обработки.
- [ ] Пустой или синтаксически неверный JSON даёт 400.
- [ ] Массив вместо верхнеуровневого объекта даёт 400.
- [ ] `request_id` заголовка и тела обязан совпадать.
- [ ] Неподдерживаемая версия даёт 409.
- [ ] Пустой `items` и 101 элемент отклоняются.
- [ ] Неизвестное поле версии 1 отклоняется.

### 4.3. Время и защита

- [ ] Текущая временная метка принимается.
- [ ] Значение за пределом 300 секунд даёт 401.
- [ ] Неверный формат времени подписи даёт 401.
- [ ] Старое `occurred_at` принимается.
- [ ] `occurred_at` более чем на пять минут в будущем отклоняется по элементу.
- [ ] `occurred_at` создаётся при первой успешной долговечной записи во vtelemax и не меняется при повторных HTTP-попытках того же `event_id`.
- [ ] Время пакетной отправки и время приёма SAGUR не подменяют `occurred_at`.
- [ ] Ограничение частоты возвращает 429 и `Retry-After` без потери очереди отправителя.
- [ ] Журнал отказа не содержит секрет и полное тело.

### 4.4. Поэлементный результат

Собрать один пакет с корректным событием, неизвестной интерактивностью, неверным действием и повтором.

- [ ] HTTP-ответ равен 200 для корректной оболочки.
- [ ] У каждого элемента есть `index`.
- [ ] Корректный элемент создаётся несмотря на соседний отказ.
- [ ] Неизвестная интерактивность даёт `interaction_not_found`.
- [ ] Неизвестный код даёт `action_unsupported`.
- [ ] `c` для `rating_menu` и `m` для `rating_coupons` дают `action_not_allowed_for_button_set`.
- [ ] Общий статус равен `partial` при смешанном результате.
- [ ] Успешные элементы не откатываются.

### 4.5. Идемпотентность

- [ ] Первое событие даёт `accepted` и одну строку.
- [ ] Тот же `event_id` с тем же значимым содержимым даёт `duplicate` и не создаёт строку.
- [ ] Изменение `request_id`, `sent_at`, порядка или соседей пакета не превращает повтор в новое событие.
- [ ] Тот же `event_id` с другим `interaction_id`, действием, временем или `provider_message_id` даёт `event_id_conflict`.
- [ ] Два конкурентных одинаковых запроса создают не более одной строки.

## 5. Формирование сообщения SAGUR

### 5.1. Наборы

- [ ] «Без кнопок» создаёт только `DispatchTask`.
- [ ] `rating_menu` создаёт одну интерактивность с действиями `l`, `d`, `m`.
- [ ] `rating_coupons` создаёт одну интерактивность с действиями `l`, `d`, `c`.
- [ ] Задача и интерактивность появляются одной транзакцией.
- [ ] Ошибка одной из двух вставок откатывает рабочую пару.
- [ ] Набор хранится у конкретной интерактивности, а не как список строк кнопок.

### 5.2. Служебный JSON

- [ ] Для каждой новой кнопки построен объект версии 2 `t/v/i/a`.
- [ ] `i` равен `MessageInteraction.id`, а не UUID задачи и не идентификатор провайдера.
- [ ] `a` принадлежит закрытому перечню `ldm/dlm/mld/ldc/dlc/cld`; первый символ совпадает с фактически нажатой кнопкой, вся строка — с выбранным набором.
- [ ] Сериализация не содержит необязательных пробелов и дополнительного кодирования.
- [ ] Пример версии 2 с `i=123456` занимает 37 байт.
- [ ] Максимальный положительный 64-битный `i` занимает 50 байт для каждого из шести значений.
- [ ] vtelemax продолжает принимать версию 1 с одиночным действием для ранее отправленных сообщений.
- [ ] Перед провайдером выполняется фактическая проверка длины UTF-8.
- [ ] Идентификатор отсутствует в видимой надписи.

### 5.3. Исторические маршруты

- [ ] Для `historical_telegram_channel` интерактивность не создаётся.
- [ ] Для `legacy_vtelemax_channel` интерактивность не создаётся.
- [ ] Для `mailing_row_external_id` интерактивность не создаётся.
- [ ] В форме исторической рассылки набор кнопок недоступен.
- [ ] Серверная защита работает при обходе формы или старых некорректных данных.
- [ ] Историческая прогревающая рассылка продолжает отправляться обычным способом.

### 5.4. Ошибка формирования

- [ ] Неверный набор, действие, длина или платформенная структура не вызывает программный интерфейс мессенджера.
- [ ] Задача получает диагностируемую ошибку.
- [ ] Сообщение не отправляется только с текстом.
- [ ] Ошибка одной интерактивной задачи не останавливает независимые обычные задачи.

## 6. Проверка vtelemax без SAGUR

### 6.1. Разбор

- [ ] Одинаковая общая функция разбирает обезличенные реальные структуры Telegram, VK и MAX.
- [ ] Проверяются точные `t`, `v`, `i`, `a` и отсутствие лишних полей.
- [ ] Строка с двоеточиями или нижними подчёркиваниями не принимается как схема версии 1.
- [ ] Чужие кнопки продолжают обрабатываться существующими маршрутами.

### 6.2. Локальная очередь

- [ ] Событие записывается до пользовательского ответа.
- [ ] `event_id` создаётся один раз и сохраняется во всех повторах HTTP.
- [ ] Повтор одного обратного вызова платформы возвращает прежнюю строку.
- [ ] Новое реальное повторное нажатие создаёт новый `event_id`.
- [ ] Два обработчика не создают дубль одного события платформы.
- [ ] Недоступная локальная база не выдаёт ложного успешного приёма.

### 6.3. Пользовательские действия

- [ ] `c` вызывает существующее общее меню купонов и ничего не применяет.
- [ ] `m` вызывает существующее главное меню напрямую.
- [ ] `m` не запускает регистрацию, приветствие и другие действия `/start`.
- [ ] `m` отправляет новое меню, не заменяя исходную рассылку.
- [ ] После `m` до оценки можно позже нажать `l` или `d`.
- [ ] После оценки остаётся только соответствующая `c` либо `m`.
- [ ] Ошибка изменения клавиатуры не удаляет уже записанное событие.

## 10. Первая оценка и конкурентность

Для одной интерактивности создать почти одновременные `l` и `d` с разными `event_id`:

- [ ] В таблице две попытки.
- [ ] Только одна имеет `result=accepted`.
- [ ] Вторая имеет `rating_already_recorded`.
- [ ] Основной отчёт увеличен ровно на одну оценку.
- [ ] Диагностика показывает обе попытки.

Повторить с несколькими процессами SAGUR и PostgreSQL. Результат должен обеспечиваться ограничением базы, а не порядком одного процесса.

Затем:

- [ ] Нажать `m` либо `c` до оценки — право оценки сохраняется.
- [ ] Нажать навигационную кнопку после оценки несколько раз — все реальные нажатия учитываются.
- [ ] Нажать кнопку сообщения годичной давности — событие принимается.

## 11. Пакетная работа и отказоустойчивость

### 11.1. Плановый цикл

- [ ] Одиночное нажатие хранится локально и отправляется в ближайшем окне примерно пяти минут.
- [ ] Пустая очередь не создаёт HTTP-запрос.
- [ ] Достижение 100 строк не запускает мгновенную отправку само по себе.
- [ ] Более 100 строк делятся на последовательные пакеты.
- [ ] Тело каждого пакета не превышает 65 536 байт.
- [ ] Одновременно выполняется не более одного запроса.
- [ ] Новые запросы исходно отправляются не чаще одного в секунду.

### 11.2. SAGUR недоступен

- [ ] Остановить или изолировать точку SAGUR.
- [ ] Нажатие всё равно получает локальное пользовательское действие vtelemax.
- [ ] Событие остаётся `pending` или `retry`.
- [ ] Задержка растёт от 30 секунд, но не выше 3600 секунд, с разбросом.
- [ ] После восстановления тот же `event_id` принимается.
- [ ] Событие не удаляется из-за числа временных попыток.

### 11.3. Частичный ответ

- [ ] Принятые, повторные и повторная оценка подтверждаются локально.
- [ ] Отклонённый элемент переводится в `blocked`, но не удаляется.
- [ ] Элемент без результата остаётся для повтора.
- [ ] Подтверждённые элементы не отправляются снова вместе с ошибочным.

### 11.4. Классы ошибок

- [ ] 413 приводит к уменьшению пакета.
- [ ] 429 учитывает `Retry-After`.
- [ ] 5xx и сетевой тайм-аут повторяются.
- [ ] 400, 401, 403, 409 и 415 сохраняют строки и создают операционное предупреждение.
- [ ] Секрет и полные тела отсутствуют в ошибках.

## 12. Смена HMAC-секрета

В контролируемой среде выполнить согласованную смену:

- [ ] Подтвердить одинаковый общий резервный секрет без его вывода.
- [ ] Очистить специализированный секрет на обеих сторонах.
- [ ] Проверить подписанный пакет через общий секрет.
- [ ] Установить новый специализированный секрет на обеих сторонах.
- [ ] Проверить новый подписанный пакет.
- [ ] Убедиться, что события, попавшие в короткий промежуток 401, сохранились и были повторены.
- [ ] Проверить очередь на отсутствие потерянных и постоянно заблокированных строк.

Если эксплуатация потребует полностью исключить даже краткий 401, это оформляется отдельным расширением для одновременного принятия предыдущего секрета; первая версия не считается имеющей такую возможность.

## 13. Отчёты SAGUR

### 13.1. Простая рассылка

- [ ] Показаны технически успешные сообщения с кнопками.
- [ ] Показаны уникальные взаимодействовавшие сообщения или гости.
- [ ] `l` и `d` считают только `accepted`.
- [ ] Уникальные и общие `m` разделены.
- [ ] Знаменатель доли подписан.
- [ ] Сообщения без кнопок и исторические сообщения в знаменатель не входят.

### 13.2. Купонная рассылка

- [ ] Уникальные открывавшие купоны и все `c` показаны отдельно.
- [ ] Повторные `c` увеличивают только общий счётчик.
- [ ] Применение купона остаётся отдельным показателем iiko/OLAP.
- [ ] Нажатие `c` не увеличивает использование купона.

### 13.3. Купонный автосценарий

- [ ] Те же показатели доступны в отчёте сценария.
- [ ] Фильтрация по сценарию не смешивает другие отправки гостя.
- [ ] Оценки, открытия купонов и фактическое применение не смешаны.

### 13.4. Терминология

- [ ] Нет нового показателя «Прочитали».
- [ ] Используются «Взаимодействовали», «Поставили оценку», «Открыли купоны» и «Открыли меню».
- [ ] `DispatchTask.done` не изменяется после нажатия.

## 14. Диагностика и наблюдаемость

- [ ] `audit_message_interactions_readiness --as-json` работает без изменений данных.
- [ ] `--fail-on-blocked` возвращает ненулевой код при блокировке.
- [ ] `--require-enabled` отличает подготовленный, но выключенный контур от готового к пилоту.
- [ ] `pilot_message_interaction` без `--confirm` ничего не создаёт и не отправляет.
- [ ] Подтверждённый пилот требует одного явно заданного гостя и бота.
- [ ] `diagnose_message_interactions` ищет по `interaction_id`, `event_id`, рассылке и сценарию.
- [ ] Диагностика показывает принятую и повторную оценку, `c`, `m` и ошибку без секретов.
- [ ] В vtelemax видны состояния и возраст исходящей очереди.
- [ ] `request_id` позволяет сопоставить безопасные журналы обеих систем без таблицы входящих пакетов.

## 15. Нагрузочная и регрессионная проверка

- [ ] Создана представительная крупная современная рассылка с кнопками.
- [ ] Измерены две пакетные вставки задач и интерактивностей.
- [ ] Диспетчер по-прежнему выбирает пакет из 200 задач индексным планом.
- [ ] Не появилось нового полного просмотра `dispatch_tasks`.
- [ ] Обычная рассылка без кнопок не получила статистически значимого ухудшения.
- [ ] Пакет 100 событий укладывается в допустимое время и размер.
- [ ] Смешанный пакет не удерживает одну общую долгую транзакцию.
- [ ] Конкурентные оценки не создают взаимных блокировок вне одной интерактивности.
- [ ] Отчёты крупной кампании имеют проверенный `EXPLAIN (ANALYZE, BUFFERS)`.
- [ ] Новые индексы добавлены только на основании измерений.

Регрессия:

- [ ] Универсальная очередь без кнопок работает как раньше.
- [ ] Исторические рассылки работают как раньше.
- [ ] Простые, купонные и сценарные отчёты без интерактивности работают как раньше.
- [ ] Регистрация и welcome-купон vtelemax не затронуты.
- [ ] Главное меню и `/start` сохраняют прежние отдельные смыслы.

## 16. Откат

- [ ] Отключение `MESSAGE_INTERACTIONS_ENABLED` прекращает только новые кнопки.
- [ ] Удаление одной платформы из разрешённого списка не останавливает обычные сообщения этой платформы.
- [ ] Ранее отправленные кнопки продолжают приниматься.
- [ ] vtelemax продолжает отправлять накопленную очередь.
- [ ] Таблицы и события не удаляются.
- [ ] После повторного включения не образуются дубли `event_id`.

Входящая точка отключается только при проблеме безопасности. Обычный функциональный откат оставляет её включённой для старых сообщений.
