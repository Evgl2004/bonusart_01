# F0-F1: Подготовка проекта и миграционное ядро универсальной очереди

## Цель этапа

На первом шаге мы не ломаем существующий контур обработки веб-хуков и не трогаем рабочую бизнес-логику.
Задача этапа:

1. Подготовить техническую базу под новую архитектуру.
2. Перейти к управляемой схеме через Django Migrations.
3. Ввести новые сущности данных для очередей и мультибот-каналов.

## F0. Подготовка локальной среды

Требование: использовать локальное виртуальное окружение `venv`.

Стандартные команды:

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Примечание по текущему окружению Codex: в момент выполнения этапа команды `python`/`py` не найдены в `PATH`,
поэтому создание `venv` из текущего терминала заблокировано. Это не мешает подготовке кода и миграций,
но перед локальным запуском нужно добавить установленный Python в `PATH` или указать полный путь к `python.exe`.

## F1. Новые модели (через Django migrations)

Добавлены управляемые модели:

1. `BotProfile` (`bot_profiles`)
2. `GuestBotBinding` (`guest_bot_bindings`)
3. `DispatchTask` (`dispatch_tasks`)

### 1) `BotProfile`

Назначение: справочник подключенных ботов по провайдерам `telegram/max/vk`.

Ключевые поля:

1. `code` — уникальный технический код профиля.
2. `provider_type` — тип провайдера.
3. `token`, `settings` — параметры интеграции.
4. `is_active` — флаг активности.

### 2) `GuestBotBinding`

Назначение: связь гостя с ботом и маршрутом доставки сообщения.

Ключевые поля:

1. `external_chat_id` — целевой чат/peer провайдера.
2. `is_primary` — признак основного бота для повседневных отправок.
3. `is_opt_in`, `is_stop_sending` — управление коммуникацией.

Ограничения:

1. Уникальная пара `(guest, bot)`.
2. Только один `is_primary=True` на одного гостя (частичный unique constraint).

### 3) `DispatchTask`

Назначение: универсальная задача на отправку, независимая от источника.

Ключевые поля:

1. `source_type` — источник (`mailing/webhook/manual/system`).
2. `provider_type` — провайдер доставки (`telegram/max/vk`).
3. `priority` — приоритет (`high/normal/bulk`).
4. `status` — статус жизненного цикла задачи.
5. `idempotency_key` — дедупликация повторных постановок.
6. `available_at` — момент, когда задачу можно брать в работу.
7. `attempt`, `max_attempts` — контроль ретраев.

Индексы и ограничения:

1. Индекс "lane" по `provider_type + priority + status + available_at`.
2. Индекс по `status + available_at` для выборки готовых задач.
3. Проверка `attempt <= max_attempts`.

## Что это даёт уже сейчас

1. Переход к эволюции схемы через миграции, а не через ad-hoc SQL.
2. Чёткую модель мультиботов и "основного бота".
3. Нейтральную задачу `DispatchTask` как основу диспетчера.

## Что пойдёт следующим этапом (F2)

1. Redis-диспетчер и физические lane-очереди `high/normal/bulk` внутри каждого провайдера.
2. Роутинг задач из массовых рассылок и веб-хуков в универсальное ядро.
3. Feature flag для безопасного включения нового контура без поломки текущего.
