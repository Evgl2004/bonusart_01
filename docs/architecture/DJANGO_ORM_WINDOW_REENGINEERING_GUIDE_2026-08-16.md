# Оконные функции Django ORM: правила реинжиниринга и диагностики

Дата фиксации: 2026-08-16.

## Назначение

Документ закрепляет проверенный подход к переносу группировки, выбора одной
строки из группы, сортировки и ограничения результата из Python в PostgreSQL.
Он применяется к интерактивным формам, отчётам и другим сценариям только после
проверки бизнес-эквивалентности на реальных данных.

Текущая опорная конфигурация проекта:

- Django 5.2.7;
- PostgreSQL 17.5 в рабочем окружении;
- запросы строятся только через Django ORM, прямой SQL не используется.

Оконные функции не являются новым для проекта механизмом. В сервисе купонных
автосценариев `guests/services/coupon_autoscenarios.py` функции
`_last_order_venue_map()` и `_last_order_visit_at_map()` уже применяют
`Window(RowNumber())`. Эта реализация появилась в коммитах `e922931` от
2026-06-08 и `05533a5` от 2026-06-09.

## Когда подход оправдан

Оконный ORM-запрос подходит, когда необходимо:

1. выбрать первую или последнюю строку внутри группы;
2. определить победителя по нескольким бизнес-приоритетам;
3. построить рейтинг или верхние N строк внутри группы;
4. сохранить строки результата и одновременно использовать агрегаты группы;
5. избежать переноса большого промежуточного набора в память приложения.

Для простой фильтрации, одной общей агрегации или небольшого справочника окно
само по себе преимуществ не даёт. Решение принимается по измерениям, а не по
предположению, что один сложный запрос всегда быстрее нескольких простых.

## Проверенная схема запроса

Для отбора любимого или последнего заведения используется следующая
последовательность:

1. Отфильтровать допустимую аудиторию, период и положительные факты.
2. Сгруппировать строки до уровня «гость × заведение».
3. Посчитать агрегаты `Sum` и `Max`.
4. Внутри каждого гостя назначить `RowNumber` по полному детерминированному
   порядку.
5. Через `FirstValue` вынести идентификатор победителя в оконную аннотацию.
6. Во внешнем запросе оставить ранг 1 и сравнить победителя с выбранным
   заведением.
7. Явно задать итоговый `order_by()` и только после этого применять срез,
   который становится SQL-ограничением `LIMIT`.

PostgreSQL вычисляет оконные функции после `WHERE`, `GROUP BY`, `HAVING` и
агрегатов. Поэтому фильтр по вычисленному рангу требует внешнего запроса. Django
формирует такой квалифицирующий внешний запрос автоматически при фильтрации по
оконной аннотации.

Проверку выбранного заведения нельзя помещать в исходный `WHERE`: тогда до
ранжирования исчезнут конкурирующие заведения гостя, и каждое посещённое
заведение сможет ошибочно стать победителем.

## Обязательные правила корректности

1. **Полный порядок.** Последним критерием должен быть стабильный уникальный или
   однозначный признак. В текущем отборе ничья разрешается через
   `department_id`; без этого результат при равных бизнес-показателях не
   гарантирован.
2. **Единая спецификация окна.** Если `RowNumber` и `FirstValue` определяют
   одного победителя, им передаётся один общий словарь `partition_by` и
   `order_by`. Это предотвращает незаметное расхождение правил.
3. **Фильтрация через И (`AND`).** Django 5.2 поддерживает фильтры по оконным
   выражениям, но не поддерживает неоднородные дизъюнктивные условия
   `OR`/`XOR` при одновременной агрегации. Текущий внешний фильтр намеренно
   является конъюнкцией.
4. **Явная итоговая сортировка.** Порядок внутри окна не определяет порядок
   строк всего результата. Верхний `order_by()` обязателен до `LIMIT`.
5. **Осознанная рамка (`frame`).** `FirstValue` использует рамку окна. В текущем
   запросе стандартная рамка безопасна: она начинается с первой строки
   детерминированно отсортированного раздела, поэтому первое значение одинаково
   для всех рассматриваемых строк. Расширять рамку до всего раздела без
   необходимости не следует, поскольку это может увеличить буферизацию.
6. **Одинаковая область данных.** Период и допустимая аудитория применяются до
   агрегации ко всем конкурирующим строкам, а не только к целевому заведению.
7. **Контроль числа запросов.** Без внутреннего лимита сервис выполняет один
   запрос. При необходимости одновременно знать полный размер и получить
   ограниченный список допустимы отдельный `COUNT` и основной запрос с
   `LIMIT`; это должно быть явно отражено в контракте сервиса.
8. **Проверка на рабочей СУБД.** SQLite-тесты проверяют бизнес-логику, но не
   заменяют проверку синтаксиса, плана и времени на PostgreSQL той же основной
   версии, что используется в эксплуатации.

## Производительность и индексы

Оконная функция обычно требует сортировки внутри разделов. При росте объёма
следует проверять узлы `WindowAgg`, `Sort`/`Incremental Sort`, фактическое число
строк, циклов, объём памяти и возможную сортировку на диск.

Новый индекс не добавляется только из-за наличия `ORDER BY`. В текущей задаче
порядок включает результаты `Sum` и `Max`, которые появляются после
агрегации, поэтому обычный индекс таблицы фактов не может заранее полностью
выдать итоговый порядок. Индекс или отдельная агрегатная витрина рассматриваются
только после подтверждённого ухудшения плана на рабочих объёмах.

## Повторно используемый протокол диагностики

Диагностический скрипт для интерактивной формы или отчёта должен:

1. работать только на чтение и не создавать рассылки, задания или иные записи;
2. не выводить телефоны, идентификаторы чатов и другие персональные данные;
3. сравнивать новый запрос с понятным контрольным алгоритмом на одном и том же
   исходном наборе;
4. сравнивать не только количество, но и полную упорядоченную сигнатуру строк;
5. отдельно проверять ничьи, пустые аудитории, периоды, ограничения аудитории и
   все бизнес-режимы;
6. прогреть оба варианта, затем выполнять не менее пяти чередующихся запусков и
   сравнивать медианы, чтобы уменьшить влияние кеша и единичных выбросов;
7. фиксировать структуру скомпилированного Django QuerySet: наличие окон,
   внешнего фильтра, верхнего `ORDER BY`, `LIMIT` и число обращений к таблице;
8. исследовать план штатным `QuerySet.explain()`, а `analyze=True` применять
   только когда выполнение запроса безопасно;
9. отклонять вариант при любом несовпадении бизнес-результата независимо от
   ускорения;
10. считать замер диагностикой конкретного объёма данных, а не нагрузочным
    тестом или гарантией будущей производительности.

Такой протокол допускается повторно использовать для отчётов, рейтингов,
последних событий и устранения дублей. Для каждого нового сценария контрольный
алгоритм и критерии эквивалентности формулируются заново.

## Ограничение `QuerySet.explain()` в текущей версии проекта

В Django 5.2.7 на QuerySet, где внешний квалифицирующий запрос фильтрует оконную
аннотацию, локально воспроизведено формирование вложенного двойного `EXPLAIN`,
которое PostgreSQL не принимает. Рабочее выполнение QuerySet этим не затронуто.

До отдельного обновления Django диагностика разделяется:

- точный итоговый QuerySet компилируется Django ORM и проверяется структурно;
- план исследуется через `QuerySet.explain()` для того же агрегатно-оконного
  этапа до внешнего фильтра;
- точный итоговый QuerySet выполняется обычным способом для сравнения состава,
  порядка и времени;
- прямой SQL как обход ограничения не используется.

После обновления Django это поведение нужно проверить заново и убрать обход,
если он больше не требуется.

## Зафиксированный положительный результат

Проверка отбора заведений на рабочем PostgreSQL от 2026-08-16 подтвердила полное
совпадение состава и порядка аудитории с контрольным алгоритмом. Для аудитории
новых ботов с окном 180 дней все восемь комбинаций «режим × заведение» стали
быстрее на 27,25–43,78% по медиане пяти чередующихся запусков. Для исторической
аудитории ускорены шесть из восьми комбинаций; оставшиеся отклонения +0,20% и
+4,94% не показали существенной регрессии. План содержит `WindowAgg`, одно
чтение таблицы дневных фактов и не содержит коррелированного подзапроса.

Полные условия и результаты проверки зафиксированы в документе
`docs/operations/HISTORICAL_TELEGRAM_VENUE_FILTERS_2026-08-16.md`.

## Версия Django и отдельный риск обновления

Проект закреплён на Django 5.2.7. Официальная ветка 5.2 LTS к 2026-08-16 имеет
версию 5.2.17; между ними опубликованы исправления безопасности. Это не является
дефектом оконного алгоритма, но оставлять зависимость без отдельной оценки
обновления не следует.

Обновление Django не входит в данный реинжиниринг. Его нужно выполнять отдельной
задачей: изучить все промежуточные примечания к выпускам, обновить зависимость в
ветке, прогнать полный рекурсивный профиль тестов и повторить PostgreSQL-
диагностику оконных QuerySet.
