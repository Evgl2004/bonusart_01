# F23: MAILINGS UI BLUEPRINT (MVP)

Дата: 2026-04-23  
Статус: согласовано, запуск в реализацию

## 1. Цель этапа

Собрать понятный пользовательский контур работы с рассылками в новом интерфейсе:
1. без переключения между legacy-экранами;
2. с прозрачным флоу от гипотезы до запуска и контроля;
3. без изменения ядра backend-пайплайна доставки.

## 2. Целевой пользовательский флоу

1. Маркетолог формирует гипотезу в `guests/workbench` (фильтры, сегменты, категории, условия).
2. Создает черновик рассылки по отбору.
3. Переходит в `mailings-v2` и настраивает кампанию:
3.1. шаблон;
3.2. окно отправки;
3.3. ботов/каналы;
3.4. приоритет.
4. Проверяет аудиторию перед запуском:
4.1. всего получателей;
4.2. исключенные/дубликаты;
4.3. валидность контактов.
5. Запускает кампанию.
6. Контролирует выполнение в мониторе:
6.1. очередь;
6.2. статусы доставки;
6.3. ошибки и ретраи.
7. Анализирует результат и корректирует следующую гипотезу.

## 3. Каркас экранов (MVP)

1. `mailings-v2/campaigns`
1.1. список кампаний;
1.2. быстрые статусы;
1.3. переходы в редактирование и монитор.

2. `mailings-v2/campaigns/new`, `mailings-v2/campaigns/<id>`
2.1. единая форма кампании;
2.2. базовые проверки перед запуском.

3. `mailings-v2/campaigns/<id>/audience`
3.1. превью аудитории;
3.2. контроль состава перед отправкой.

4. `mailings-v2/templates`
4.1. список шаблонов;
4.2. создание/редактирование;
4.3. предпросмотр и валидация переменных.

5. `mailings-v2/monitor`
5.1. агрегаты по задачам отправки;
5.2. ошибки по типам;
5.3. переход в детальные логи.

6. `mailings-v2/scenarios`
6.1. список автосценариев;
6.2. активность, последний запуск, ошибки.

## 4. Принципы реализации

1. Не дублировать backend-логику доставки: использовать существующие модели и команды.
2. Вводить экран за экраном, с обратной совместимостью через legacy URL.
3. Любое действие изменения состояния (запуск/пауза/перезапуск) подтверждать заметным уведомлением.
4. Поддерживать наблюдаемость: в UI должны быть причины ошибок, а не только финальный статус.
5. Держать время ответа в рабочем диапазоне и проверять узкие места по SQL.

## 5. Что считаем готовым результатом MVP

1. Маркетолог проходит сценарий "создать и запустить кампанию" в `mailings-v2` без legacy-форм.
2. Есть рабочий монитор статусов и ошибок по кампании.
3. Есть единая точка входа в шаблоны.
4. Переходы из `workbench` в рассылки работают в новом контуре.

## 6. Нефункциональные ожидания

1. UI должен оставаться стабильным на боевом объеме данных.
2. Ошибки доставки должны быть читаемы без просмотра логов контейнеров.
3. Любая спорная метрика должна быть проверяема по данным БД и аудит-командам.

## 7. Следующий шаг реализации

Первый технический шаг F23:
1. добавить навигационный каркас `mailings-v2/*`;
2. вывести его в рабочее меню;
3. связать с текущими legacy-формами как временные bridge-точки;
4. затем перейти к полноценным экранам кампаний/шаблонов/монитора.
