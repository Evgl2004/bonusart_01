# F9: Глобальный Переход Проекта На `managed=True`

## Цель
Перевести **все модели проекта** на управление схемой через Django migrations и прекратить практику неотслеживаемых изменений структуры БД.

## Что сделано в этом этапе
1. Во всех моделях `guests/models.py`, где было `managed = False`, установлен `managed = True`.
2. Добавлена миграция `0010_alter_category_options_alter_guest_options_and_more.py`, которая фиксирует переход `managed=True` на уровне Meta-опций.
3. Добавлена миграция `0011_remove_guest_is_stop_sending_category_external_id_and_more.py` в формате `SeparateDatabaseAndState`:
   - `state_operations`: синхронизируют состояние моделей Django с текущим кодом;
   - `database_operations=[]`: не выполняют SQL-изменения в БД на этом шаге.

## Почему используется `SeparateDatabaseAndState`
Исторически часть полей и связей менялась без миграций (при `managed=False`), из-за чего состояние моделей и миграционный граф Django разошлись.

Если пытаться применить обычную автогенерируемую миграцию, есть риск:
1. конфликтов с уже существующими колонками/индексами;
2. блокирующих вопросов по `NOT NULL` полям;
3. небезопасных операций на рабочей БД.

Формат `SeparateDatabaseAndState` позволяет сначала безопасно выровнять **состояние Django**, а затем уже в следующих этапах выполнять целевые SQL-изменения строго через миграции.

## Правила после перехода
1. Любое изменение моделей выполняется только через `makemigrations` и `migrate`.
2. Прямые SQL-изменения схемы запрещены.
3. Для контроля в CI/локально обязательно использовать:
   - `python manage.py makemigrations --check --dry-run`
4. Все миграции сопровождаются русскими комментариями и понятным описанием цели.

## Следующий шаг
Подключить доступную локальную БД и выполнить проверку плана применения:
1. `python manage.py migrate --plan`
2. `python manage.py migrate`
3. Проверить, что прикладные сценарии (`dispatch`, `provider-worker`, `monitor`, `mailing`) работают на новой миграционной базе без регрессий.
